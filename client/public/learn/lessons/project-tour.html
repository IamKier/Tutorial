Tour of the task tracker Intermediate

Everything in this course, assembled. This lesson walks the whole codebase in the order that makes it make sense, then follows one keystroke from your fingers to the disk and back.

Each layer knows only about the one beneath it. app.js has no idea data lives in a file; server.js has no idea it is JSON on disk rather than Postgres. Those boundaries are what make the app changeable.

db.js — the data layer

Read this first, because everything depends on it. It exports four functions:

listTasks()              // Read
createTask(title)        // Create
updateTask(id, changes)  // Update
deleteTask(id)           // Delete

CRUD. Nearly every backend you ever write is these four operations repeated for each kind of thing in your app.

Three details worth stopping on:

The private helpers

async function readAll() { ... }    // not exported
async function writeAll(tasks) { }  // not exported

Because they are not exported, nothing outside this file can read or write the file directly. That is what makes the boundary real rather than a naming convention.

The expected error

catch (err) {
  if (err.code === 'ENOENT') return [];   // no file yet — fine on first run
  throw err;                              // anything else is a real bug
}

Catch what you expect and can handle; re-throw the rest. An empty catch {} here would turn a permissions problem into "all your tasks silently disappeared".

The allow-list

if (typeof changes.title === 'string') task.title = changes.title;
if (typeof changes.done === 'boolean') task.done = changes.done;

Not Object.assign(task, changes) — that would let a caller rewrite the id or invent fields. Mass assignment, prevented in two lines.

server.js — the backend

It does the two jobs every backend does.

Job one: hand over the files

serveStatic reads from public/ and sends the bytes with the right Content-Type. The security check is the part to remember: 

const filePath = path.join(PUBLIC_DIR, requestedPath);

if (filePath !== PUBLIC_DIR && !filePath.startsWith(PUBLIC_DIR + path.sep)) {
  res.writeHead(403);
  return res.end('403 Forbidden');
}

Without it, GET /../../db.js escapes the public folder and hands out any file on the machine.

Job two: answer the API

GET    /api/tasks       -> db.listTasks()
POST   /api/tasks       -> db.createTask(title)
PATCH  /api/tasks/:id   -> db.updateTask(id, changes)
DELETE /api/tasks/:id   -> db.deleteTask(id)

handleApi splits the path, checks the method, validates the input, calls db, and sends a response with a precise status code. That is all a router is.

The safety net

catch (err) {
  console.error('Unhandled error:', err);
  if (!res.headersSent) sendJson(res, 500, { error: 'Internal server error' });
  else res.end();
}

One catch around everything, so a bug in one handler returns a clean 500 instead of killing the process and disconnecting every other user.

public/ — the frontend

index.html

Structure only. Notice that the task list is an empty <ul> — the tasks exist only in the live DOM that app.js builds. Notice also the tiny script in the <head> that applies your saved theme before the first paint, so dark mode does not flash white.

theme.css and styles.css

theme.css holds the tokens — spacing, type, colour, motion — and is shared with this lesson site, which is why both look like one product. styles.css holds the app's own components and almost never uses a raw value.

Dark mode is eleven lines redefining tokens. No component rule changes at all.

app.js

Seven sections, and the structure survives into every framework:

  1. State — tasks, filter. The single source of truth.
  2. Elements — looked up once.
  3. API — a request() wrapper that checks response.ok, because fetch will not.
  4. Formatting — relativeTime().
  5. Render — rebuilds the list from state, every time.
  6. Events — one delegated listener on the <ul>.
  7. Startup — load().

And the one line that matters most:

title.textContent = task.title;   // never innerHTML for user input

One keystroke, all the way down

You type "Buy milk" and press Enter.

  1. app.js — the form's submit listener fires. preventDefault() stops the page reloading.
  2. app.js — the submit button is disabled so a double-click cannot create two tasks. api.create() sends POST /api/tasks with {"title":"Buy milk"}.
  3. network — the request crosses to the server. Instant on localhost; possibly slow on a train.
  4. server.js — Node calls the request handler. The path starts with /api/, so handleApi runs.
  5. server.js — POST with no id means "create". readJsonBody collects the body chunk by chunk and parses it.
  6. server.js — validation: a string, non-empty after trimming, 200 characters or fewer. Otherwise a 400 and we stop here.
  7. db.js — createTask reads the file, appends a task with a fresh UUID and ISO timestamp, writes the whole file back.
  8. server.js — sendJson(res, 201, task): status, headers, body, done.
  9. app.js — the await resumes. response.ok is true, so the JSON is parsed and returned.
  10. app.js — the server's task (with its real id) goes into tasks, and render() redraws the list.
  11. browser — layout and paint. "Buy milk" appears, animating in.
  12. app.js — finally re-enables the button and refocuses the input.

Twelve steps, four files, one round trip. Every feature you add follows this same path — which is why it is worth being able to recite it.

What is deliberately missing

Knowing the gaps is part of understanding the code:

  • No accounts. Everyone shares one list. Adding users touches every layer — it is the single most instructive next feature.
  • No tests. The exercises are manual. A real project would test db.js first, since it is pure logic.
  • No build step. The browser gets exactly the files on disk, which is why you can edit and reload with nothing in between.
  • A file, not a database. Complete with the race condition from the data lesson.
  • No rate limiting, no HTTPS, no pagination. Fine on localhost, not fine on the internet.

Exercises

These are bigger than the earlier ones. Each touches the whole stack.

1

Edit a task's title

Double-clicking a title turns it into an input; Enter saves, Escape cancels, blur saves. Then answer: how much of the backend did you have to change?

Show answer

None. PATCH /api/tasks/:id already accepts a title, and updateTask already allows it. This is the payoff for designing the API around the resource rather than around the screens that happen to exist today.

The frontend work: a dblclick listener (delegated, on the list), swap the <span> for an <input> with the current value, listen for keydown and blur, call api.update(id, { title }), then render(). Watch out for one thing: after render() the input no longer exists, so do not touch it afterwards.

2

Move filtering to the server

The filters are client-side today: the browser downloads every task and hides some. Add GET /api/tasks?status=done and use it instead. Then argue for which is better.

Show answer

With twelve tasks, client-side wins easily — switching filters is instant because no request is involved. With fifty thousand, it is indefensible: you download megabytes to show twenty rows.

The general rule is that filtering belongs where the data is. Client-side filtering is a legitimate optimisation for small, already-loaded sets, and a bug at scale. Note that the current code makes the switch cheap — visibleTasks() is the only function that would change.

3

Add projects

Give every task a project. You need a projects collection with its own CRUD, a projectId on tasks, an API that can list tasks for one project, and a UI to switch between them. Decide what happens to a project's tasks when the project is deleted.

Show answer

There is no single right answer, and choosing deliberately is the exercise. The three options for deletion:

  • Cascade — delete the tasks too. Simple, and irreversible.
  • Orphan — set projectId to null and show them in an "Inbox". Safest, and the usual choice in real apps.
  • Refuse — return 409 Conflict unless the project is empty. Annoying, but nothing is ever lost by accident.

You will also hit a design decision the file-based store makes awkward: two collections in two files with no transaction between them. Deleting a project and its tasks is two writes, and a crash between them leaves the data inconsistent. That is the moment to reach for SQLite.

Where to go next

In this order, because each one builds on the last:

  1. Express. Rewrite server.js with it. Half an hour, and every line will be familiar.
  2. SQLite via node:sqlite. Rewrite db.js, change nothing else. Then learn enough SQL to be dangerous — it has outlasted every framework and will outlast the current ones.
  3. Authentication. Sessions and cookies first, tokens later. This is where you learn to think about trust.
  4. A frontend framework — React or Svelte. Both automate the render() you wrote by hand, and you will understand what "state" means instead of memorising rules.
  5. TypeScript, once you have been burned by an undefined field at runtime. It will feel obvious by then.
  6. Deployment. Get it on the internet. Everything gets more real when someone else can open it.

One piece of advice worth more than that list: build things you actually want to use. The project you finish because you needed the thing at the end teaches more than five tutorials you abandon halfway.
