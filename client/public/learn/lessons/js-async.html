Async, promises and fetch Intermediate

This is where the frontend meets the backend, and it is the concept most people find genuinely hard. Slow down here — everything in the second half of the course depends on it.

The problem

JavaScript runs on a single thread. There is one queue, and while your code is running nothing else can — no clicks, no rendering, nothing.

So what happens when you ask a server for data and it takes 300 milliseconds to answer? If the language simply waited, the page would freeze solid every time. Instead, slow work is handed off, your code carries on, and you are notified when the result arrives.

That is what asynchronous means. Everything below is machinery for it.

Promises

A promise is an object representing a value that is not here yet. It is in one of three states: pending, then either fulfilled with a value or rejected with an error. 

const promise = fetch('/api/tasks');
console.log(promise);   // Promise { <pending> }

The original way to unwrap one:

fetch('/api/tasks')
  .then(response => response.json())
  .then(tasks => console.log(tasks))
  .catch(err => console.error(err));

async and await

The modern way, which is the same thing written to read top to bottom:

async function loadTasks() {
  try {
    const response = await fetch('/api/tasks');
    const tasks = await response.json();
    console.log(tasks);
  } catch (err) {
    console.error(err);
  }
}

Two rules and you have it:

  • await pauses this function until the promise settles. The rest of the page keeps running.
  • await only works inside an async function. And an async function always returns a promise, whatever you write in the return.
The forgotten await

Leave out await and you get the promise object instead of the value. const tasks = fetch(...) then tasks.length is undefined — no error, just nonsense. When a value is mysteriously undefined or logs as Promise {}, a missing await is the first thing to check.

Order of execution

console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');

// Prints: 1, 4, 3, 2

Synchronous code runs first and finishes. Then queued promise callbacks. Then timers. Even a zero-millisecond timeout waits for the current work to finish — "asynchronous" means "later", never "at the same time".

fetch

// GET is the default
const response = await fetch('/api/tasks');
const tasks = await response.json();

Note the two awaits. The first waits for the response headers to arrive; the second waits for the body to finish downloading and be parsed. They are separate because the headers arrive first, and sometimes that is all you need. 

// Sending data
const response = await fetch('/api/tasks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: 'Buy milk' }),
});
  • method — GET, POST, PATCH, DELETE.
  • headers — without Content-Type, most servers will not parse your body as JSON.
  • body — must be a string. JSON.stringify on the way out; the server does JSON.parse on the way in. That round trip is the API.

The trap that catches everyone

// WRONG
try {
  const response = await fetch('/api/tasks/does-not-exist');
  const task = await response.json();   // no error thrown!
} catch (err) {
  // never runs for a 404
}

fetch only rejects when the network fails. A 404 or a 500 is a perfectly successful fetch as far as the browser is concerned — you asked, the server answered. You have to check yourself: 

const response = await fetch(url);

if (!response.ok) {                    // ok is true for 200-299
  throw new Error(`Request failed (${response.status})`);
}

const data = await response.json();

This is why app.js has a request() wrapper rather than calling fetch in four places — one check, written once, impossible to forget. 

async function request(url, options = {}) {
  const response = await fetch(url, options);

  if (!response.ok) {
    let message = `Request failed (${response.status})`;
    try {
      const body = await response.json();
      if (body.error) message = body.error;   // use the server's message
    } catch { /* not JSON — the status will do */ }
    throw new Error(message);
  }

  if (response.status === 204) return null;   // No Content: empty body
  return response.json();
}

Running things at the same time

// Sequential — 300ms, then another 300ms. Total 600ms.
const a = await fetch('/api/one');
const b = await fetch('/api/two');

// Concurrent — both start immediately. Total 300ms.
const [a, b] = await Promise.all([
  fetch('/api/one'),
  fetch('/api/two'),
]);

Use Promise.all whenever requests do not depend on each other. If the second needs a value from the first, they have to be sequential.

The catch: Promise.all rejects as soon as any promise rejects, and you lose the results of the ones that succeeded. When you need every outcome regardless: 

const results = await Promise.allSettled(promises);
// [{status: 'fulfilled', value: ...}, {status: 'rejected', reason: ...}]

The "Clear done" button in the app uses Promise.all, so ten deletes take as long as the slowest one rather than ten times as long — and because a partial failure would leave the screen out of step with the server, the catch block reloads the list from scratch.

Handling the wait well

Every request takes time and every request can fail. An interface that ignores both feels broken on a slow connection. Three habits: 

button.disabled = true;         // 1. stop double-submits
try {
  const task = await api.create(title);
  tasks.unshift(task);
  render();
} catch (err) {
  showError(err.message);       // 2. tell the user, in their terms
} finally {
  button.disabled = false;      // 3. always undo it
}

finally runs whether it succeeded or threw. Without it, one failed request leaves the button disabled forever and the only fix is a reload.

Optimistic updates

Two honest approaches to the wait:

  • Wait for the server, then update the screen. Always accurate, feels slower.
  • Update immediately, then put it back if the request fails. Feels instant, and the rollback is the entire difficulty.
// Optimistic delete
const backup = [...tasks];
tasks = tasks.filter(t => t.id !== id);
render();                            // gone from the screen instantly

try {
  await api.remove(id);
} catch (err) {
  tasks = backup;                    // put it back
  render();
  showError('Could not delete that.');
}

The task tracker takes the first approach, with one cosmetic exception: the row starts fading out while the request is in flight, so it feels quick without claiming anything that has not happened yet.

Exercises

1

Talk to the API from the console

With the app open, use the DevTools console. Fetch all tasks and log them. Then create one. Then fetch again to confirm it is there. Watch each request appear in the Network tab as you go.

Show solution 
// List
const tasks = await (await fetch('/api/tasks')).json();
console.table(tasks);

// Create
const created = await (await fetch('/api/tasks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: 'From the console' }),
})).json();
console.log(created);

// Confirm
console.table(await (await fetch('/api/tasks')).json());

Note that the task appears in the file but not on screen until you reload — the page's tasks array knows nothing about what you did behind its back. That gap between client state and server state is the permanent background problem of frontend work.

2

Make fetch fail quietly

In the console, run this and explain what you see: 

const response = await fetch('/api/tasks/nope');
console.log(response.ok, response.status);
const data = await response.json();
console.log(data);

Then write a version that throws a useful error instead.

Show solution

You get false 404 and then {error: 'Task not found'}. No exception at any point — which is exactly the trap. A careless const tasks = await response.json() would hand you an error object where you expected an array, and the crash would happen somewhere else entirely. 

async function getJson(url) {
  const response = await fetch(url);
  if (!response.ok) {
    const body = await response.json().catch(() => ({}));
    throw new Error(body.error ?? `Request failed (${response.status})`);
  }
  return response.json();
}
3

Make deletes optimistic

In public/app.js, change the delete handler so the task disappears immediately and is restored if the request fails. Test the failure path by stopping the server (Ctrl+C) and then deleting a task.

Show solution 
if (event.target.closest('.task__delete')) {
  const backup = [...tasks];

  tasks = tasks.filter(t => t.id !== id);
  render();                       // instant

  try {
    await api.remove(id);
  } catch (err) {
    tasks = backup;               // put it back
    render();
    showError('Could not delete that task.');
  }
}

Note [...tasks] rather than tasks — you need a copy of the array as it was, not another reference to the one you are about to replace.

With the server stopped you will see the row vanish and reappear, with an error toast. That flicker is the honest cost of optimism: you told the user something had happened before you knew it had.
