Closures, prototypes and the event loop Expert

Three mechanisms that explain most of JavaScript's surprising behaviour. You can write code for years without naming them — and every hour spent debugging something baffling is usually one of these.

Closures

A function remembers the variables it was created next to, even after that code has finished running. 

function counter() {
  let count = 0;                    // local to this call

  return () => ++count;             // but this keeps it alive
}

const next = counter();
next();   // 1
next();   // 2

count should have gone when counter() returned. It does not, because the returned function still refers to it — so the scope survives, not just the value.

The bug everyone meets

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3

var is function-scoped, so all three callbacks close over the same i. By the time they run, the loop has finished and it is 3. 

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2

let is block-scoped and the loop creates a fresh binding each iteration, so each callback closes over its own. This is the single best argument for never using var.

The same bug in React

useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);        // count is captured once, and stays 0 forever

The empty dependency array means the effect runs once, so the callback closes over the count from the first render. It reads 0 every second and sets 1 every second. 

setCount((c) => c + 1);   // no capture: React supplies the latest

This is what people mean by a stale closure, and it is the most common genuinely hard React bug — because nothing errors and the code reads correctly.

Prototypes

JavaScript has no classes underneath. Every object has a hidden link to another object, and a property that is missing is looked for along that chain. 

const task = { title: 'Buy milk' };

task.toString;    // not on task — found on Object.prototype
task.nonsense;    // undefined: the chain ran out
task ──▶ Object.prototype ──▶ null

class is syntax over exactly this:

class Task {
  constructor(title) { this.title = title; }
  describe() { return this.title; }
}

// describe lives on Task.prototype, ONCE — not on each instance.
// Which is why 10,000 tasks do not mean 10,000 copies of the method.

this is decided by the call, not the definition

const task = {
  title: 'Buy milk',
  describe() { return this.title; },
};

task.describe();                  // 'Buy milk'

const fn = task.describe;
fn();                             // undefined — `this` is not task any more

this is whatever sits left of the dot at the moment of calling. Pull the method off the object and there is no dot, so there is no this. 

element.addEventListener('click', task.describe);        // broken
element.addEventListener('click', () => task.describe()); // fine

Arrow functions have no this of their own — they use the one from where they were written. That is exactly why they are the right choice for callbacks and the wrong choice for object methods.

The event loop

One thread. Everything queues. The order is not obvious, and knowing it explains a whole category of "why did that run first". 

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');

// 1, 4, 3, 2

The rule, in order:

  1. All synchronous code runs to completion first.
  2. Microtasks — promise callbacks, queueMicrotask. The queue is drained entirely.
  3. One macrotask — a timer, an I/O callback, an event.
  4. Back to step 2.
Microtasks can starve everything else

Because the microtask queue is drained completely before any timer runs, a promise that schedules another promise forever will freeze the page — with no infinite loop anywhere in your code: 

function spin() { Promise.resolve().then(spin); }
spin();   // the browser never repaints again

await is a queue position

async function run() {
  console.log('a');
  await null;              // yields, even though there is nothing to wait for
  console.log('b');
}

run();
console.log('c');

// a, c, b

Everything after an await is a microtask, whatever you awaited. That is why await null is occasionally used deliberately: it pushes the rest of the function behind the current synchronous work.

Where these meet in this project

  • Closure — client/src/library/runner.js keeps settled, worker and timer alive inside a promise for as long as the run lasts.
  • Event loop — the same file's timeout only starts after the worker reports ready, because starting it earlier charges worker startup to the reader's code.
  • Stale closure avoided — useTasks.js uses setTasks((current) => …) rather than closing over the array.

Exercises

1

Predict the order

console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));

queueMicrotask(() => console.log('E'));

console.log('F');
Show answer

A F C E D B

  • A, F — synchronous, so first.
  • C then E — both queued as microtasks, in the order they were scheduled.
  • D — the second .then is only queued once C has run, so it joins the back of the queue.
  • B — a timer, and no timer runs until the microtask queue is empty.

The part that catches people is D after E. Chained promises are not one unit; each link is scheduled separately.

2

Fix the loop three ways

Make this print 0, 1, 2 — once with let, once keeping var and adding a wrapper, and once without a closure at all. 

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
Show solution 
// 1. let — a fresh binding per iteration
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);

// 2. var, with an immediately-invoked function to capture a copy.
//    This is what everyone wrote before let existed.
for (var i = 0; i < 3; i++) {
  ((n) => setTimeout(() => console.log(n), 0))(i);
}

// 3. No closure: bind the value as an argument.
for (var i = 0; i < 3; i++) setTimeout(console.log, 0, i);
3

Why does this counter stick?

function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    setInterval(() => setSeconds(seconds + 1), 1000);
  }, []);

  return <p>{seconds}</p>;
}

Name both bugs.

Show answer
  1. Stale closure. seconds is captured from the first render and never updates, so it sets 1 every second forever. Fix: setSeconds((s) => s + 1).
  2. No cleanup. The interval is never cleared, so it keeps firing after the component unmounts, and every remount adds another. Fix: return () => clearInterval(id).

Both are invisible in a quick test — the number does change, once — which is what makes this pairing so common in real code.
