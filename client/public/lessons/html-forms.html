Forms and input Basics

Forms are how a page collects anything from a person. They are also the part of HTML with the most built-in behaviour — and the most often thrown away and rebuilt badly with JavaScript.

The smallest useful form

<form>
  <label for="name">Your name</label>
  <input type="text" id="name" name="name" />
  <button type="submit">Send</button>
</form>

Three things to notice, because each is doing real work:

  • The <form> wrapper. It is what makes Enter submit from inside a field. Without it you have a text box and a button that happen to sit near each other, and you have to wire up the Enter key yourself.
  • for matches id. That pairing links the label to the field, so clicking the label focuses the input, and a screen reader announces "Your name, edit text" instead of just "edit text".
  • name, not id, is what gets submitted. id is for CSS and JavaScript; name is the key the value is sent under.
Every input needs a label

A placeholder is not a label. It disappears the moment someone types, it is usually too low-contrast to read, and many screen readers ignore it. If you genuinely cannot show a label, use a visually hidden one or aria-label — but show it if you can.

Input types

type changes the keyboard on phones, the validation the browser applies, and sometimes the whole control: 

<input type="text" />         <!-- anything -->
<input type="email" />        <!-- checks for an @, email keyboard -->
<input type="password" />     <!-- masked -->
<input type="number" />       <!-- numeric keyboard, spinner -->
<input type="tel" />          <!-- phone keypad -->
<input type="url" />
<input type="date" />         <!-- a real date picker, free -->
<input type="checkbox" />
<input type="radio" />
<input type="file" />
<input type="search" />
<input type="color" />

Picking the right type is the cheapest usability win in web development. A type="email" field gives a phone user the keyboard with @ on it — no code, no library.

Beyond a single line

<textarea id="notes" name="notes" rows="4"></textarea>

<select id="priority" name="priority">
  <option value="low">Low</option>
  <option value="normal" selected>Normal</option>
  <option value="high">High</option>
</select>

<textarea> has no value attribute — its content sits between the tags. And be careful: any whitespace you put there for tidiness becomes part of the value, which is why the tags above are jammed together.

Checkboxes and radios

<!-- Checkboxes: independent. Each needs its own name. -->
<input type="checkbox" id="urgent" name="urgent" />
<label for="urgent">Urgent</label>

<!-- Radios: pick one. The SHARED name is what groups them. -->
<input type="radio" id="p-low" name="priority" value="low" />
<label for="p-low">Low</label>

<input type="radio" id="p-high" name="priority" value="high" />
<label for="p-high">High</label>

Radios with different name attributes do not group, so all of them can be selected at once. That is the classic radio button bug, and it is always this.

Validation the browser does for you

<input type="text" required />
<input type="text" minlength="3" maxlength="200" />
<input type="number" min="1" max="10" step="1" />
<input type="text" pattern="[A-Z]{3}-\d{4}" />
<input type="email" required />

Add these and the browser refuses to submit an invalid form, showing its own message, in the user's language, with no JavaScript at all. Free, and better than most hand-rolled versions.

Client-side validation is a courtesy, not a defence

Everything above runs in the browser, on the user's machine, and can be switched off in DevTools in two seconds. Anyone can send a request straight to your server without ever loading your page. So validate on the client to give people fast feedback, and validate again on the server because that is the check that actually protects your data. Look at server.js: it re-checks the title even though client/index.html already marked the input required.

Other attributes worth knowing

AttributeWhat it does
placeholderGrey hint text. Not a label.
autocomplete"off", or a hint like "email" so browsers can autofill correctly.
autofocusFocus this field on load. Use at most once, and not on mobile — it pops the keyboard up unasked.
disabledUnusable and not submitted.
readonlyUnchangeable but still submitted.

What submitting actually does

This is the part worth understanding properly, because it explains a line you will write in every JavaScript form handler.

By default, submitting a form makes the browser navigate — it builds an HTTP request from the fields and loads a whole new page with the response. Two attributes control it: 

<form action="/api/tasks" method="post">
  • method="get" — values go in the URL as ?title=Buy+milk. For searches and filters: the URL is shareable and bookmarkable.
  • method="post" — values go in the request body. For anything that changes data. Not visible in the URL, not left in browser history.

That full-page reload is how the web worked for its first decade, and it still works fine. But in an app like the task tracker we want the page to stay put, so we cancel the default and send the request ourselves: 

form.addEventListener('submit', (event) => {
  event.preventDefault();   // stop the browser navigating
  // ...send it with fetch instead
});

Forget preventDefault() and the page flashes, reloads and clears the input every time. It is one of the most common first-week bugs, and now you know exactly what it is.

Grouping related fields

<fieldset>
  <legend>Delivery address</legend>

  <label for="street">Street</label>
  <input type="text" id="street" name="street" />

  <label for="city">City</label>
  <input type="text" id="city" name="city" />
</fieldset>

<fieldset> and <legend> tie a group together. It matters most for radio buttons: without it a screen reader announces "Low" and "High" with no clue what they are choosing between.

Exercises

1

A sign-up form

Build a form with a name (required, at least 2 characters), an email (required, correct type), a password (required, at least 8 characters), a date of birth, a select for country with three options, and a required "I agree to the terms" checkbox. Every field labelled properly. Try to submit it empty and see what the browser says.

Show solution 
<form>
  <label for="name">Full name</label>
  <input type="text" id="name" name="name" minlength="2" required />

  <label for="email">Email</label>
  <input type="email" id="email" name="email" autocomplete="email" required />

  <label for="password">Password</label>
  <input type="password" id="password" name="password" minlength="8" required />

  <label for="dob">Date of birth</label>
  <input type="date" id="dob" name="dob" />

  <label for="country">Country</label>
  <select id="country" name="country">
    <option value="ph">Philippines</option>
    <option value="sg">Singapore</option>
    <option value="jp">Japan</option>
  </select>

  <input type="checkbox" id="terms" name="terms" required />
  <label for="terms">I agree to the terms</label>

  <button type="submit">Create account</button>
</form>
2

Watch a GET submit

Give a form method="get" with two text inputs named q and sort. Fill them in, submit, and look at the address bar. Now change to method="post" and submit again. What changed, and why is GET the right choice for a search box?

Show answer

With GET the values appear in the URL as ?q=shoes&sort=price. That URL can be bookmarked, shared and re-loaded, which is exactly what you want for a search result. With POST the URL stays clean and the values travel in the body — right for anything that changes something, because a URL that creates data when opened is a URL that fires again every time someone hits reload.

3

Find it in the project

Open client/index.html and find the composer form. Which attributes limit what can be typed? Then open server.js and find where the same rule is enforced again. Why is it in both places?

Show answer

The HTML uses required and maxlength="200". In server.js, handleApi rejects a title that is empty after trimming or longer than 200 characters with a 400. The client copy makes the app feel responsive — you find out instantly, without a round trip. The server copy is the one that actually protects the data, because the client can be bypassed entirely.
