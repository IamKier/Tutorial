Tracking changes Basics

Git remembers every version of every file, so you can change anything without the fear that you will not be able to get back. That fear is what makes people keep folders called project-final-v2-REAL.

The three places a file can be

Almost every confusing thing about Git comes from not knowing which of these a file is in: 

  working tree          staging area           repository
  (your files)          (what goes next)       (committed history)
       │                       │                      │
       │──── git add ─────────▶│                      │
       │                       │──── git commit ─────▶│
       │◀────────────── git checkout ─────────────────│
  • Working tree — the files as they are on disk right now.
  • Staging area — the changes you have chosen for the next commit. Git's own name for it is the "index".
  • Repository — every commit ever made, in .git/.

The staging area is the part other version control systems do not have, and the part people find pointless at first. Its purpose: you can make five changes and commit only two of them, so a commit is one idea rather than one afternoon.

Starting

git init                    # start tracking this folder
git status                  # what has changed, and what is staged
git add server.js           # stage one file
git add .                   # stage everything changed
git commit -m "Add server"  # record the staged changes
git log --oneline           # the history, one line each

git status is the one to run constantly. It tells you which of the three places everything is in, and it suggests the command for whatever you probably want next.

What a commit is

Not a diff — a complete snapshot of every tracked file, plus a pointer to the commit before it. That is why moving between versions is instant: Git is not replaying changes, it is checking out a stored state. 

git log --oneline

e8e21d3 Add a catalogue checker instead of a database
78f75e8 Pin the masthead, and give it a real height
4f3a20c Add a main page between the cover and the shelf

That hex string is a hash of the commit's entire content — the files, the message, the author, the time, and the parent commit. Change any of it and the hash changes, which is what makes history tamper-evident.

Writing a message worth reading

You are writing to whoever runs git log in a year, and that is usually you. 

❌ fix
❌ updates
❌ asdf
❌ fixed the thing that was broken

✅ Fix blank page: malformed regex crashed the app on load
✅ Pin the masthead, and give it a real height

The shape that works:

  • A short first line, around fifty characters, in the imperative — "Add", "Fix", "Remove", as though completing the sentence "this commit will…".
  • A blank line, then as much detail as the change deserves.
  • Say why, not what. The diff already shows what changed. It cannot show what you were trying to achieve, or what you tried first that did not work.
The test for a good message

Imagine finding this commit while hunting a bug at midnight. Does the message tell you whether this is the change that broke it? "Updates" never does.

Undoing things

This is the table worth keeping. The four situations are genuinely different:

You want toCommand
Discard changes to a filegit restore file.js
Unstage, but keep the changesgit restore --staged file.js
Change the last commit's messagegit commit --amend
Undo a commit, keep the changesgit reset --soft HEAD~1
Undo a commit and its changesgit reset --hard HEAD~1
Undo a pushed commitgit revert <hash>
reset --hard is the one that loses work

It throws away uncommitted changes with no confirmation and no undo. Run git status first, every time — if it says nothing is modified, there is nothing to lose.

And use revert rather than reset for anything you have pushed. revert makes a new commit that undoes the old one, so the history everyone else has stays valid. reset rewrites history, and rewriting history other people are standing on is how you ruin an afternoon for a whole team.

.gitignore

# Dependencies — rebuilt from the lock file
node_modules/

# Build output — derived from source
dist/

# The database. Never commit this: it holds real data.
data/

# Secrets, by definition
.env

Three rules that cover almost everything:

  • Never commit what you can rebuild — node_modules, dist. It bloats the repository and causes conflicts nobody can resolve.
  • Never commit secrets. And note that deleting them later does not help: they remain in history, and history is what gets cloned.
  • Do commit the lock file. package-lock.json is what makes two machines install the same code.

Line endings

Windows ends lines with CRLF and everything else with LF. Left alone, a file edited on two machines shows up as every line changed. 

# .gitattributes
* text=auto eol=lf

Settling it in .gitattributes rather than in each person's config means it applies to everyone who clones. This project has exactly that file, for exactly that reason.

Exercises

1

Make a repository and break it

In an empty folder: git init, create a file, commit it. Change it, check git status, then git restore it. Change it again, stage it, then unstage it. Watch what git status says at each step.

Show solution 
git init
echo "hello" > notes.txt
git add notes.txt
git commit -m "Add notes"

echo "changed" >> notes.txt
git status                     # "modified: notes.txt", not staged
git restore notes.txt          # gone; the file is back to the commit

echo "again" >> notes.txt
git add notes.txt
git status                     # "modified: notes.txt", staged
git restore --staged notes.txt # unstaged, but the edit is still there
git status                     # modified again, not staged

The pair worth internalising: restore discards the edit, restore --staged only un-chooses it. One loses work, the other does not.

2

Stage half a change

Edit two files. Stage only one, and commit it. Confirm with git log and git status that the other is still waiting. Why is this worth being able to do?

Show answer

Because you rarely do exactly one thing at a time. You set out to fix a bug, notice a typo, and rename a variable on the way. Committing all three together means that when the bug fix turns out to be wrong, undoing it also undoes the typo fix.

git add -p goes further and stages selected hunks within a file, so one file's changes can go into two commits.

3

Read this project's history

Run git log --oneline in the Tutorial folder. Find the commit that fixed the blank page. Then run git show <hash> on it. Does the message tell you what went wrong without reading the diff?

Show answer

It should: the message names the cause (a regex that threw at module load), the symptom (React never mounted), and the reason it went unnoticed (every other check was green). That is the "why, not what" rule — the diff shows a changed line, and only the message can tell you that the change was one word in a regular expression.
