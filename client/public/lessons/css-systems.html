Variables, themes, responsive Intermediate

This is the difference between a page that is styled and a product that has a design. Nothing here is difficult — it is about deciding your values once and then refusing to invent new ones.

Custom properties

CSS has real variables. They start with two dashes:

:root {
  --accent: #4f46e5;
  --space-4: 1rem;
  --radius: 12px;
}

.button {
  background: var(--accent);
  padding: var(--space-4);
  border-radius: var(--radius);
}

:root is the <html> element, so anything defined there is available to the whole document. And unlike a variable in a preprocessor, these are live in the browser — change one at runtime and everything using it updates immediately. 

/* Read and write from JavaScript */
const styles = getComputedStyle(document.documentElement);
styles.getPropertyValue('--accent');

document.documentElement.style.setProperty('--accent', 'tomato');

They cascade and can be overridden per component:

.card { --padding: 1rem; padding: var(--padding); }
.card--roomy { --padding: 2rem; }   /* same rule, new value */

And they take a fallback for when the variable is not defined:

color: var(--brand, #333);

Tokens

A design system is mostly a short list of allowed values, which people call tokens. Open client/public/theme.css — the whole first section is nothing but this: 

:root {
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-5: 1.5rem;
  --space-6: 2rem;
  --space-7: 3rem;
}

Note that the scale is not 1, 2, 3, 4 — it grows by roughly a factor each step. That is what the eye reads as deliberate. Every gap and padding in the project comes from that list, and the moment you catch yourself typing padding: 13px, the design has started to drift.

The same applies to type, radius, shadow and motion:

--text-sm: 0.875rem;
--text-base: 0.9375rem;
--text-lg: 1.125rem;

--radius-sm: 8px;
--radius: 12px;

--ease: cubic-bezier(0.2, 0, 0.2, 1);
--fast: 120ms;
--slow: 220ms;

Two durations and one curve, reused everywhere, is what makes an interface feel like one hand made it. Twelve different durations feel like a committee.

Dark mode

Here is the payoff. Define the colours as tokens:

:root {
  --bg: #f7f8fa;
  --surface: #ffffff;
  --text: #14171c;
  --border: #e5e7ec;
}

Then redefine only those tokens for dark, and every rule in the project follows:

@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) {
    --bg: #0e1013;
    --surface: #16191e;
    --text: #e9ecf1;
    --border: #262b34;
  }
}

Not one component rule changes. That is why the tokens are worth the setup.

Letting the user choose

prefers-color-scheme follows the operating system. To offer a toggle as well, you need a second selector, because there are two ways to end up in dark mode: 

/* a) the OS says dark, and the user has not overridden it */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) { --bg: #0e1013; ... }
}

/* b) the user pressed our toggle */
:root[data-theme='dark'] { --bg: #0e1013; ... }
// The toggle itself is three lines
const next = current === 'dark' ? 'light' : 'dark';
document.documentElement.dataset.theme = next;
localStorage.setItem('theme', next);
The flash of the wrong theme

If you apply the saved theme from a script at the bottom of the page, the browser paints the light version first and then switches — a white flash on every load. The fix is a tiny blocking script in the <head> that sets the attribute before the first paint. Both pages in this project do exactly that; it is the very first script tag in client/index.html.

Responsive design

Write the flexible version first, then adjust:

/* Base: works everywhere */
.layout { display: grid; grid-template-columns: 17rem 1fr; }

/* Adjust below 60rem */
@media (max-width: 60rem) {
  .layout { grid-template-columns: 1fr; }
}

Pick breakpoints where your layout stops working, not at named device sizes. Drag the window slowly and change it at the width where it starts to look wrong — there is no iPhone-shaped constant worth memorising.

Use rem for breakpoints rather than px, so they scale with a reader's chosen font size.

Media queries beyond width

@media (prefers-color-scheme: dark) { }
@media (prefers-reduced-motion: reduce) { }
@media (hover: none) { }          /* touch device — no hover at all */
@media print { }

hover: none is genuinely useful. In this project the delete button on a task only appears on hover — which on a touchscreen would mean never. That media query shows it permanently on touch devices, asking the device about its capabilities instead of guessing from screen width.

Doing without breakpoints

width: min(40rem, 100%);        /* the smaller of the two */
padding: max(1rem, 3vw);        /* the larger of the two */
font-size: clamp(1rem, 2.5vw, 2rem);  /* min, preferred, max */

clamp() scales a value smoothly between two limits with no media query at all. Combined with the auto-fill grid from the layout lesson, a surprising amount of responsive work disappears.

Transitions and animation

.button {
  background: var(--accent);
  transition: background var(--fast) var(--ease);
}

.button:hover {
  background: var(--accent-hover);
}

The transition goes on the resting state, not the hover state. Put it on :hover and it animates on the way in but snaps back on the way out.

Animate transform and opacity, nothing else

Those two are handled by the GPU without re-running layout. Animating width, height, top or margin forces the browser to recalculate the position of everything on every frame, and that is where jank comes from. Need to slide something? transform: translateX(), not left. 

@keyframes slide-up {
  from { opacity: 0; transform: translateY(0.5rem); }
  /* no `to` needed — it animates to the element's normal state */
}

.toast { animation: slide-up 220ms var(--ease); }

Respect reduced motion

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}

Some people get motion sick from interface animation and their OS lets them say so. Note the 0.01ms rather than 0 — it keeps any JavaScript waiting on a transitionend event working, while removing the movement.

Naming

This project uses BEM — block, element, modifier — which is a convention, not a tool: 

.composer          /* block: a component */
.composer__input   /* element: a part of it */
.composer--wide    /* modifier: a variation */

It looks verbose. The payoff is that you can read any class in the stylesheet and know exactly where it applies without hunting through the HTML, and two components can never collide.

And keep state in one class on the parent:

.task.is-done .task__title { text-decoration: line-through; }

JavaScript toggles the single word is-done and CSS decides what that means. The alternative — JavaScript setting style.textDecoration directly — scatters your design across two languages and makes dark mode nearly impossible.

Exercises

1

Tokenise a stylesheet

Rewrite this using custom properties so the palette lives in one place:

.header { background: #4f46e5; color: white; padding: 16px; }
.button { background: #4f46e5; color: white; padding: 8px 16px;
          border-radius: 8px; }
.link   { color: #4f46e5; }
.badge  { background: #4f46e5; color: white; padding: 4px 8px;
          border-radius: 8px; }
Show solution 
:root {
  --accent: #4f46e5;
  --on-accent: #ffffff;
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-4: 1rem;
  --radius-sm: 8px;
}

.header { background: var(--accent); color: var(--on-accent);
          padding: var(--space-4); }
.button { background: var(--accent); color: var(--on-accent);
          padding: var(--space-2) var(--space-4);
          border-radius: var(--radius-sm); }
.link   { color: var(--accent); }
.badge  { background: var(--accent); color: var(--on-accent);
          padding: var(--space-1) var(--space-2);
          border-radius: var(--radius-sm); }

Rebranding is now one line instead of four, and it cannot be done half-way.

2

Add dark mode to it

Extend your answer above with --bg, --surface and --text, then make it respond to the OS dark mode setting. Test by switching your system theme.

Show solution 
:root {
  --bg: #f7f8fa;
  --surface: #ffffff;
  --text: #14171c;
  --accent: #4f46e5;
}

@media (prefers-color-scheme: dark) {
  :root {
    --bg: #0e1013;
    --surface: #16191e;
    --text: #e9ecf1;
    --accent: #7c76ff;   /* lifted: indigo is too dark on black */
  }
}

body { background: var(--bg); color: var(--text); }

Note the accent changes too. A colour picked for a white background is usually too dark on a black one — dark mode is not an inversion, it is a second palette.

Retheme the app

Open client/public/theme.css and change --accent, --accent-hover and --accent-soft to a green. Reload the task tracker. How many places changed, and how many lines did you edit? Then find every rule in client/src/styles/app.css that would have needed editing without variables.

Without tokens that is a find-and-replace across two files, in two themes, and the one you miss is always the hover state nobody screenshots.
