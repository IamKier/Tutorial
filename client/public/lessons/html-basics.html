HTML: the basics Basics

HTML answers exactly one question: what things are on this page? Not what they look like — that is CSS — and not what they do, which is JavaScript. Keeping those three jobs apart is the oldest good idea in web development.

An element

Almost everything in HTML is an element, and an element looks like this:

<p>Hello, world</p>
 ↑      ↑        ↑
 |      |        closing tag
 |      the content
 opening tag

The tag name says what kind of thing it is. <p> is a paragraph, <h1> is a top-level heading, <button> is a button. The browser already knows how each one should behave.

A few elements have no content and so no closing tag — they are called void elements: 

<img src="cat.jpg" alt="A cat asleep on a keyboard" />
<br />
<input type="text" />

Attributes

Attributes go in the opening tag and configure the element. They are always name="value": 

<a href="https://example.com" target="_blank">Visit example</a>
<img src="logo.png" alt="Our logo" width="120" />
<input type="email" name="email" required />

Four attributes you will use constantly:

AttributeWhat it does
idA unique name for one element. JavaScript finds elements by it.
classA label you can put on many elements. CSS styles by it.
href / srcWhere a link goes; where an image or script comes from.
altWhat an image shows, for people who cannot see it.
An id must be unique

Two elements with the same id is invalid HTML, and getElementById will silently return only the first one. If you want to label a group of elements, that is what class is for.

Nesting

Elements go inside other elements, and that nesting forms a tree. Indent it and the structure becomes obvious: 

<article>
  <h2>Making bread</h2>
  <p>It takes <strong>four</strong> ingredients.</p>
  <ul>
    <li>Flour</li>
    <li>Water</li>
    <li>Salt</li>
    <li>Yeast</li>
  </ul>
</article>

Tags must close in the reverse of the order they opened — innermost first. This is wrong, even though it often still renders: 

<p><strong>Overlapping</p></strong>   <!-- wrong -->
<p><strong>Correct</strong></p>        <!-- right -->

That tree is called the DOM — the Document Object Model — and it is what JavaScript walks around in later. Every parent/child relationship you write here becomes one you can navigate in code.

The shape of a page

Every HTML document has the same skeleton:

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>My page</title>
    <link rel="stylesheet" href="/styles.css" />
  </head>
  <body>
    <h1>Visible content goes here</h1>
    <script src="/app.js"></script>
  </body>
</html>

Line by line, because every one of these earns its place:

  • <!DOCTYPE html> — tells the browser to use modern standards. Leave it out and you get a 1990s compatibility mode that breaks layouts in ways that are genuinely hard to debug.
  • lang="en" — lets screen readers pick the right pronunciation and lets browsers offer translation.
  • charset="UTF-8" — how to decode the bytes. Without it, accented characters and emoji turn to mojibake. It must be within the first 1024 bytes, which is why it goes first.
  • viewport — without this line, phones render your page as a shrunken desktop site. It is the one-line foundation of responsive design.
  • <head> holds information about the page; <body> holds what you see.
See it for real

Open public/index.html in the project. It is exactly this skeleton with more inside the body. Everything above the <body> tag is boilerplate you will type a hundred times.

The elements worth memorising

Text

<h1>Page title</h1>        <!-- one per page -->
<h2>A section</h2>
<h3>A subsection</h3>

<p>A paragraph of text.</p>
<strong>Important</strong>   <!-- bold, and means it -->
<em>Emphasised</em>          <!-- italic, and means it -->
<code>someVariable</code>
<br />                        <!-- a line break -->

Headings must not skip levels — h1 then h3 is wrong. Screen reader users navigate a page by jumping between headings, and a gap reads as a missing section. Pick the level for the structure, not the size; CSS sets the size.

Lists

<ul>                    <!-- unordered: bullets -->
  <li>Flour</li>
  <li>Water</li>
</ul>

<ol>                    <!-- ordered: numbers -->
  <li>Mix</li>
  <li>Knead</li>
</ol>

Only <li> may be a direct child of a list. Lists are everywhere in real apps — the task tracker renders its tasks into a <ul>, because a list of things is exactly what it is.

Links and images

<a href="/about">Same site</a>
<a href="https://developer.mozilla.org">Another site</a>
<a href="#section-2">Jump to an id on this page</a>

<img src="/cat.jpg" alt="A ginger cat asleep on a keyboard" />
<img src="/divider.png" alt="" />   <!-- decorative: empty alt -->
Getting alt text right

Describe the purpose, not the picture. For a photo, say what it shows. For a purely decorative image, use alt="" — that tells a screen reader to skip it. Leaving alt off entirely is the worst option, because then the screen reader reads out the filename.

Grouping

<div>A generic block. Starts on a new line.</div>
<span>A generic inline piece, sits within text.</span>

div and span mean nothing at all. They are for when you need a box to hang styling on and no meaningful element fits. Reach for them last — the semantics lesson covers the meaningful ones and why they are worth the effort.

Comments

<!-- This is not shown on the page -->

Comments are visible to anyone who views the page source. Never put anything private in one.

Whitespace collapses

HTML squashes any run of spaces, tabs and newlines into a single space. These two produce identical output: 

<p>Hello        world</p>

<p>Hello
   world</p>

So indent your HTML freely for readability — it costs nothing. And when you need space on the page, that is a CSS job (margin, padding), never a row of &nbsp;.

A recipe page

Build a page with: a main heading, a paragraph of introduction, a subheading "Ingredients" with a bulleted list of four, a subheading "Method" with a numbered list of three steps, and a link at the bottom to another site. Bold one ingredient using <strong>.

2

Read a real page

Open public/index.html from the project. Find the <ul> that holds the tasks. Why is it empty in the file even though tasks appear on screen? Then right-click the running app and choose "Inspect" — how does what you see there differ from the file?

Show answer

The file is empty because JavaScript builds the list at runtime and inserts it into the live page. "View source" shows the file as it was sent; "Inspect" shows the DOM as it is now, including everything JavaScript has added. Learning to tell those two apart saves a lot of confusion later.

3

Break it on purpose

In your scratch file, delete the </p> from one paragraph and reload. Then remove <!DOCTYPE html> and reload. Then put an <li> outside any list. Inspect each result. What did the browser do about your mistakes?

Show answer

It quietly repaired them. Browsers are extraordinarily forgiving — they have to be, because most of the web is malformed. That sounds convenient and is actually a trap: your page may render fine while the DOM is not the shape you think, and then a CSS selector or a querySelector call fails for no visible reason. Write valid HTML and you never spend an evening on that particular bug.
