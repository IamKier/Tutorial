Building a REST API Intermediate

An API is a contract: these URLs exist, they accept this, they return that. Design it well and the frontend almost writes itself. Design it badly and every screen needs a special case.

What REST actually means

Strip away the arguments and it comes to this: URLs name things, methods say what to do to them. 

GET    /api/tasks       list them
POST   /api/tasks       create one
GET    /api/tasks/:id   read one
PATCH  /api/tasks/:id   change one
DELETE /api/tasks/:id   remove one

A plural noun for the collection, the same noun plus an id for one item. Once you follow that, another developer can guess your API before reading its documentation — which is the entire point of a convention. 

❌ /api/getTasks           the verb belongs in the method
❌ /api/task/delete/5      same
❌ /api/tasksList          pick one and stick to it
✅ /api/tasks
✅ /api/tasks/5

Nesting shows a relationship:

GET  /api/projects/7/tasks     tasks belonging to project 7
POST /api/projects/7/tasks     create one there

Stop at one level. /api/users/1/projects/7/tasks/3/comments is a URL nobody can read; once you have the task id, /api/tasks/3/comments says the same thing.

Routing by hand

"Routing" sounds grand. It is: look at the method and path, decide which function runs. 

async function handleApi(req, res, url) {
  const { method } = req;

  // '/api/tasks/abc-123' -> ['api', 'tasks', 'abc-123']
  // filter(Boolean) drops the empty strings the slashes create.
  const segments = url.pathname.split('/').filter(Boolean);
  const resource = segments[1];   // 'tasks'
  const id = segments[2];         // the id, or undefined

  if (resource !== 'tasks') {
    return sendJson(res, 404, { error: 'Unknown API resource' });
  }

  // Collection routes: /api/tasks
  if (!id) {
    if (method === 'GET') return sendJson(res, 200, await db.listTasks());
    if (method === 'POST') return createTask(req, res);
    return sendJson(res, 405, { error: `Method ${method} not allowed` });
  }

  // Item routes: /api/tasks/:id
  if (method === 'PATCH') return updateTask(req, res, id);
  if (method === 'DELETE') return deleteTask(res, id);
  return sendJson(res, 405, { error: `Method ${method} not allowed` });
}

Express does the same job with less typing:

app.get('/api/tasks', handler);
app.post('/api/tasks', handler);
app.patch('/api/tasks/:id', handler);

Its router is a more capable version of those if-statements. Having written them once, you know what it is doing rather than trusting it.

Validate everything

This is the part that separates a toy from something you can deploy.

const body = await readJsonBody(req);

// 1. Right type?
const title = typeof body.title === 'string' ? body.title.trim() : '';

// 2. Present?
if (!title) {
  return sendJson(res, 400, { error: 'A non-empty "title" is required' });
}

// 3. Within limits?
if (title.length > 200) {
  return sendJson(res, 400, { error: 'Title must be 200 characters or fewer' });
}
The browser form is not a defence

Your page marks the field required. That helps honest users and stops nobody else — anyone can send a request straight to your API with PowerShell, curl or Postman, and never load your page at all. Every single input has to be re-checked here.

Never trust the shape either

// DANGEROUS
Object.assign(task, changes);

// SAFE — copy only the fields you mean to allow
if (typeof changes.title === 'string') task.title = changes.title;
if (typeof changes.done === 'boolean') task.done = changes.done;

With the first version, a request body of {"id": "someone-elses-id", "isAdmin": true} writes whatever it likes into your record. This is called mass assignment, and it has caused real breaches at real companies. An allow-list is the fix, and it is three lines.

Answering consistently

function sendJson(res, statusCode, data) {
  const body = JSON.stringify(data);
  res.writeHead(statusCode, {
    'Content-Type': 'application/json; charset=utf-8',
    'Content-Length': Buffer.byteLength(body),
  });
  res.end(body);
}

One helper, used everywhere, means you cannot forget a header on one route. Note Buffer.byteLength rather than body.length — a string's length counts characters, and an emoji or an accented letter is more than one byte. Get that wrong and the client waits for data that never comes.

Keep errors in one predictable shape:

{ "error": "Title must be 200 characters or fewer" }

Because the frontend can then always read body.error. Look at the request() wrapper in client/src/api.js: it pulls that field out and shows it in the toast, so the server's message reaches the user unchanged.

Errors and the catch-all

const server = http.createServer(async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);

  try {
    if (url.pathname.startsWith('/api/')) await handleApi(req, res, url);
    else await serveStatic(res, url);
  } catch (err) {
    console.error('Unhandled error:', err);

    // headersSent guards against responding twice, which throws. If a handler
    // already started sending, the only thing left to do is hang up.
    if (!res.headersSent) {
      sendJson(res, 500, { error: 'Internal server error' });
    } else {
      res.end();
    }
  }
});

Without this, one bug in one handler takes down the whole process and disconnects everybody. With it, that request gets a clean 500 and the server carries on.

Never send the raw error to the client

{ error: err.message } looks helpful and leaks file paths, library versions and sometimes SQL. Log the detail on the server where you can read it; send the user a generic message. The exceptions are the validation errors you wrote deliberately — those are meant to be read.

Serving files safely

The other half of server.js, and it contains the sharpest edge:

const filePath = path.join(PUBLIC_DIR, requestedPath);

if (filePath !== PUBLIC_DIR && !filePath.startsWith(PUBLIC_DIR + path.sep)) {
  res.writeHead(403);
  return res.end('403 Forbidden');
}

Without that check, GET /../../db.js — or worse, /../../../../etc/passwd — escapes your public folder and hands out any file on the machine. It is called path traversal, it is decades old, and it still ships regularly.

Two details in that check:

  • Resolve first, then verify the result is inside the folder. Never try to strip .. out of the string — attackers have a long list of encodings for it.
  • The trailing path.sep matters: without it, a folder called public-secret next to public would also pass, because its path starts with the same letters.

Query parameters

// GET /api/tasks?status=done&limit=10
const status = url.searchParams.get('status');
const limit = Number(url.searchParams.get('limit')) || 50;

Use the path for what you want and the query string for which ones — filtering, sorting, pagination. And validate these too: ?limit=99999999 is a denial-of-service waiting to happen, so cap it.

What comes next in a real API

  • Authentication — who is this? Sessions with cookies first; tokens later.
  • Authorisation — may this user touch this record? Check on every request, not just at login.
  • Rate limiting — cap requests per IP, or one script can flatten you.
  • Pagination — never return an unbounded list. It is fine with twelve tasks and fatal with fifty thousand.
  • CORS — only if the frontend is served from a different origin. It is not needed here because one server does both.
  • Versioning — /api/v1/tasks, so you can change the contract without breaking old clients.

Exercises

1

Design the endpoints

Sketch the URLs and methods for a blog with posts and comments: list posts, read one, create one, edit one, delete one, list a post's comments, add a comment, delete a comment. No implementation — just the contract.

Show solution 
GET    /api/posts
POST   /api/posts
GET    /api/posts/:id
PATCH  /api/posts/:id
DELETE /api/posts/:id

GET    /api/posts/:id/comments
POST   /api/posts/:id/comments
DELETE /api/comments/:commentId

Note the last one. Deleting a comment is nested under /comments, not under its post — once you have the comment's own id, the post adds nothing but length. Nest to find things, not to act on things you can already identify.

2

Add a filter

Make GET /api/tasks?status=done work in server.js. Accept done, active and nothing at all; reject anything else with a 400. Test it from PowerShell.

Show solution 
if (method === 'GET') {
  const status = url.searchParams.get('status');

  if (status && !['done', 'active'].includes(status)) {
    return sendJson(res, 400, {
      error: 'status must be "done" or "active"',
    });
  }

  let tasks = await db.listTasks();
  if (status === 'done') tasks = tasks.filter(t => t.done);
  if (status === 'active') tasks = tasks.filter(t => !t.done);

  return sendJson(res, 200, tasks);
}
Invoke-RestMethod -Uri "http://localhost:3000/api/tasks?status=done"

Rejecting unknown values rather than silently ignoring them is deliberate: a typo like ?status=complete should tell you it is wrong, not quietly return everything and leave you wondering why the filter does nothing.

3

Attack your own server

Try each of these against the running app and explain what protects you:

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks" -Method Post `
  -ContentType 'application/json' -Body '{"title":""}'

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks" -Method Post `
  -ContentType 'application/json' -Body '{"title":123}'

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks" -Method Post `
  -ContentType 'application/json' -Body 'not json at all'

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks/xyz" -Method Patch `
  -ContentType 'application/json' -Body '{"id":"hijacked","done":true}'
Show answer
  1. 400. The title is empty after trimming.
  2. 400. The typeof body.title === 'string' check rejects a number before anything else looks at it.
  3. 500. JSON.parse throws, the catch-all turns it into a clean error. Arguably it should be a 400 — malformed input is the caller's mistake. Try fixing that.
  4. 404, because there is no task xyz. Try it with a real id: the task updates, but the id field is untouched — updateTask copies only title and done. That is the mass-assignment guard doing its job.
