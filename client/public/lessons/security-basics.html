The holes worth knowing Intermediate

Almost every breach you read about is one of a handful of mistakes, made again. This chapter is those mistakes, each with the line of code that prevents it.

The one rule underneath all of them

Never trust input. Not from a form, not from a URL, not from your own frontend, not from a response you asked for.

The one people find surprising is the third. Your page validates the title and marks the field required — and none of that reaches the server. Anyone can send a request directly: 

Invoke-RestMethod -Uri http://localhost:3000/api/tasks -Method Post `
  -ContentType 'application/json' -Body '{"title":""}'

Client-side validation is a courtesy: it tells honest users what is wrong without a round trip. The server's check is the one that protects the data. You need both, and only one of them is security.

1. Cross-site scripting

Content a user typed gets treated as markup, and their code runs in everyone else's browser. 

// The hole
title.innerHTML = task.title;

// A task titled:  <img src=x onerror="alert(document.cookie)">
// runs in every visitor's browser, on your domain, with their session.
// The fix, in one word
title.textContent = task.title;

textContent puts the string on the page as text. innerHTML parses it as HTML. That is the whole difference.

React escapes anything you interpolate, so {task.title} is safe by default and you have to reach for dangerouslySetInnerHTML to lose that. The name is doing its job.

Stored is worse than reflected

A title goes to the server, into the database, and back out to everyone who loads the list. One injection, every visitor. That is a stored XSS — and the fix was still one word.

2. SQL injection

// The hole
db.prepare(`SELECT * FROM tasks WHERE title = '${input}'`);

// Input:  ' OR 1=1 --      matches every row
// Input:  '; DROP TABLE tasks; --
// The fix
db.prepare('SELECT * FROM tasks WHERE title = ?').all(input);

A placeholder is not escaping. The value travels separately from the statement, so the database treats it as data and can never parse it as SQL — whatever is in it.

The input that finds this hole is usually not an attack. It is a customer called O'Brien, whose apostrophe closes the string and breaks the query. If ordinary names crash your app, an attacker has already been told where to push.

3. Mass assignment

// The hole
Object.assign(task, req.body);

// Body: {"title":"x","userId":"someone-else","isAdmin":true}
// The fix: copy only what you meant to allow
if (typeof changes.title === 'string') task.title = changes.title;
if (typeof changes.done === 'boolean') task.done = changes.done;

Forwarding a request body into an update lets the caller write any column, including the ones deciding who owns a record and who is an administrator. An allow-list is three lines and cannot be forgotten once written.

4. Path traversal

// The hole
const file = path.join(PUBLIC_DIR, req.url);
// GET /../../src/config.js   escapes the folder entirely
// The fix: resolve first, then check where you ended up
const file = path.join(PUBLIC_DIR, requested);

if (file !== PUBLIC_DIR && !file.startsWith(PUBLIC_DIR + path.sep)) {
  throw new HttpError(403, 'Forbidden');
}

Two details. Never try to strip .. out of the string — there are more encodings of it than you will think of. And the trailing path.sep matters: without it, a sibling folder called public-secret passes, because its path starts with the same characters.

5. Passwords

// Wrong: stored as typed
// Wrong: SHA-256 — designed to be fast, so billions of guesses a second
// Wrong: one salt for everything

// Right
const salt = crypto.randomBytes(16);
const hash = await scrypt(password, salt, 64, { N: 16384, r: 8, p: 1 });

Four properties, and each blocks a different attack:

  • Hashed, never stored. A stolen database should not be a list of passwords.
  • Slow on purpose. scrypt, bcrypt or Argon2 — never a general-purpose hash.
  • A random salt each. Two people with the same password get different hashes, so cracking one reveals nothing about the other.
  • Compared in constant time. === stops at the first differing byte, and that timing difference leaks the hash one byte at a time. Use crypto.timingSafeEqual.

6. Telling attackers things

// Leaks which emails have accounts
if (!user) throw new Error('No account with that email');
if (!valid) throw new Error('Wrong password');

// Says nothing either way
if (!user || !valid) throw new HttpError(401, 'Invalid email or password');

Timing leaks the same thing more quietly. Verifying a password takes about 100ms; skipping it for an unknown address makes that response measurably faster, so an attacker can enumerate your users without guessing a single password. The fix is to hash anyway, against a dummy value that cannot match.

The same applies to errors reaching the client:

// Leaks file paths, library versions, sometimes SQL
sendJson(res, 500, { error: err.message });

// Log the detail where you can read it; send a sentence
console.error(err);
sendJson(res, 500, { error: 'Something went wrong' });

7. Cross-site request forgery

You are logged in here. You visit a malicious page. It submits a hidden form to our API, and the browser attaches your session cookie because that is what browsers do.

Two defences, and this project uses both:

Set-Cookie: sid=...; HttpOnly; SameSite=Lax; Secure
  • SameSite=Lax — the browser will not send the cookie with a cross-site POST at all.
  • Require JSON on writes. An HTML form can only send three content types, and application/json is not one of them; sending JSON cross-origin needs a preflight the server never approves.

HttpOnly is doing separate work: JavaScript cannot read the cookie, so an XSS hole cannot walk off with the session.

8. Content-Security-Policy

Content-Security-Policy: default-src 'self'; script-src 'self'

The browser refuses to run script from anywhere but your origin — so even a successful injection has nothing to execute.

'unsafe-inline' on script-src throws it away

It is the usual quick fix when a policy blocks an inline <script>, and it removes most of the protection you added the header for. Move the script to a file instead — which is why this project's theme script lives in boot.js rather than in the page.

style-src 'unsafe-inline' is a much smaller concession: injected CSS can restyle a page but cannot execute anything.

The rest of the checklist

  • Rate limit anything that writes or authenticates.
  • Cap the request body, or one endless upload exhausts your memory.
  • Scope every query by the current user, in the SQL — not in a check a route might forget.
  • HTTPS everywhere. Over plain HTTP, every header and body is readable by anyone on the network.
  • Keep dependencies few and current. Every package is code you did not read, running with your privileges.

Exercises

1

Find the hole in each

// A
app.get('/file', (req, res) => res.sendFile(__dirname + req.query.name));

// B
const user = db.prepare(`SELECT * FROM users WHERE email = '${email}'`).get();

// C
res.send(`<h1>Results for ${req.query.q}</h1>`);

// D
if (!user) return res.status(404).send('No such user');
if (!await verify(password, user.hash)) return res.status(401).send('Wrong password');
Show answer
  • A — path traversal. ?name=/../../.env. Resolve the path, then check the result is inside the folder.
  • B — SQL injection. Use a placeholder. It also breaks on any address containing an apostrophe.
  • C — reflected XSS. The query string goes straight into HTML. Escape it, or build the DOM with textContent.
  • D — user enumeration. Two different responses tell an attacker which emails exist. One message for both, and hash even when the user is missing so the timing matches.
2

Prove the XSS, then prove the fix

Run the app. Add a task called <img src=x onerror="alert(1)"> — nothing happens. Now edit client/src/library/enhance.js, change the span.textContent in highlight() to innerHTML, rebuild, and open any chapter. Change it back.

Show answer

With innerHTML the browser parses the code sample as markup rather than showing it. On a lesson page that means the examples stop being visible; with content a user typed it means their script runs.

Worth noticing which way round the safety is. Hand-written DOM code is safe only if you remember textContent every single time. React is safe unless you deliberately opt out. Same protection, opposite defaults — and defaults are what you get on a tired afternoon.

3

Attack the running API

Try each of these against the local app and explain what stopped it:

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks" -Method Post `
  -ContentType 'application/json' -Body '{"title":123}'

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks/xyz" -Method Patch `
  -ContentType 'application/json' -Body '{"id":"hijacked","done":true}'

Invoke-WebRequest -Uri "http://localhost:3000/../../src/config.js"

Invoke-RestMethod -Uri "http://localhost:3000/api/tasks" -Method Post `
  -ContentType 'application/x-www-form-urlencoded' -Body 'title=hack'
Show answer
  1. 400. typeof body.title === 'string' rejects a number before anything else looks at it.
  2. 404 for an unknown id. With a real one it updates, but id is ignored — the allow-list in updateTask copies only title, done and dueAt.
  3. 404 or 403. The traversal guard in static.js, and the client normalising the path before it is even sent.
  4. 415. The JSON content-type requirement — which is the CSRF defence, since an HTML form cannot produce that content type.
