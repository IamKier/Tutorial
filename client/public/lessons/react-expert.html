Rendering, performance and escape hatches Expert

When React is slow it is almost always doing exactly what you told it to. This chapter is about seeing what that is — and about the times the right answer is to step outside React entirely.

When a component re-renders

Three reasons, and only three:

  1. Its own state changed.
  2. Its parent re-rendered.
  3. A context it consumes changed.

The second is the one that surprises people. A parent re-rendering re-renders every child, whether or not their props changed. That is usually fine — React compares the result and touches little DOM — but it is the root of most "why is this slow".

Identity, not equality

<TaskList tasks={tasks} onSelect={() => pick(id)} />

That arrow function is a new function on every render. So is {{ color: 'red' }}, and so is tasks.filter(...). React compares props with Object.is — identity, not contents — so a memoised child sees a changed prop every single time and re-renders anyway. 

const onSelect = useCallback(() => pick(id), [id]);
const visible = useMemo(() => tasks.filter((t) => !t.done), [tasks]);
memo without stable props does nothing

Wrapping a child in React.memo while passing it a fresh inline function is the most common wasted optimisation in React. The comparison runs, finds a different function, and re-renders — so you have added cost and gained nothing.

Either memoise the props too, or do not memoise the child.

Measure before optimising

Install React DevTools, open the Profiler, record an interaction. It shows which components rendered, how long each took, and — most usefully — why each one rendered.

The order to work in:

  1. Is anything actually slow? Sixteen milliseconds a frame is the budget. Under it, stop.
  2. Is it rendering too often, or rendering too slowly? Different problems, different fixes.
  3. Too often — find the unstable prop or the state that lives too high.
  4. Too slowly — the component is doing real work; memoise the calculation, or do less of it.

Guessing here is unusually bad, because the intuitive fix — wrapping everything in useMemo — adds comparisons and allocations to every render and frequently makes things measurably worse.

Moving state down beats memoising

// A keystroke here re-renders the whole page
function Page() {
  const [query, setQuery] = useState('');
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ExpensiveList />
    </>
  );
}
// The state lives where it is used, so the list never re-renders
function SearchBox() {
  const [query, setQuery] = useState('');
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}

function Page() {
  return (<><SearchBox /><ExpensiveList /></>);
}

No memo, no useCallback, no dependency arrays — and it is faster than either. Restructuring beats memoising. Reach for the hooks when you cannot move the state.

Keys, properly

{tasks.map((t, i) => <Row key={i} task={t} />)}

With an index key, deleting the first item shifts every key. React concludes that row 0's content changed rather than that row 0 was removed, so it reuses the existing DOM elements — including any state inside them.

The symptom: you delete a task and a checkbox two rows down is suddenly ticked, or the text you were typing appears in a different row. It looks like a data bug and it is a reconciliation bug. 

{tasks.map((t) => <Row key={t.id} task={t} />)}

There is one deliberate use of a changing key: forcing a remount. Change the key and React discards the old component and its state entirely. 

<Editor key={documentId} />   {/* a new document starts fresh */}

Escape hatches

Sometimes the right answer is to stop letting React manage something. This project has a worked example, and it was a bug first. 

// React owns these children and re-applies the HTML on every render
<article dangerouslySetInnerHTML={{ __html: html }} />

Enhancing that markup — adding syntax colours, Run buttons, heading ids — and then calling setState made React re-apply the raw HTML and wipe every change. Silently, with no error. 

// React renders it empty; we own what goes inside
<article ref={articleRef} />

useLayoutEffect(() => {
  articleRef.current.innerHTML = html;
  setHeadings(enhance(articleRef.current));
}, [html]);

React owns the container, or you own the contents. Pick one. The same rule applies to any third-party library that writes to the DOM — a chart, a map, an editor. Give it an empty element and never render children into it.

useLayoutEffect, and when it earns its cost

useEffect runs after the browser paints; useLayoutEffect runs before. The latter blocks painting, so it is the wrong default — but it is right whenever the difference would be visible as a flicker, which is exactly the case above.

Concurrent rendering

const [query, setQuery] = useState('');
const deferred = useDeferredValue(query);

// The input updates immediately; the expensive list lags behind
<input value={query} onChange={(e) => setQuery(e.target.value)} />
<Results query={deferred} />

React can now abandon a render in progress if something more urgent arrives. useDeferredValue marks a value as low priority, so typing stays responsive while the heavy list catches up when there is time.

This is also why <StrictMode> double-invokes effects in development: a render that can be interrupted and restarted must be safe to run twice, and the double-invocation surfaces the code that is not.

Exercises

1

Why is memo doing nothing?

const Row = React.memo(function Row({ task, onToggle, style }) { /* … */ });

function List({ tasks }) {
  return tasks.map((t) => (
    <Row
      key={t.id}
      task={t}
      onToggle={() => toggle(t.id)}
      style={{ padding: 8 }}
    />
  ));
}
Show answer

Two props are new objects on every render: the arrow function and the style object. Object.is says they differ, so every row re-renders and the memo only adds a comparison. 

// Hoist what never changes
const ROW_STYLE = { padding: 8 };

// Pass the id and let the child call back, so no closure is created per row
<Row key={t.id} task={t} onToggle={toggle} style={ROW_STYLE} />
// inside Row: onClick={() => onToggle(task.id)}
2

Reproduce the index-key bug

Render a list of three items, each with its own <input>, keyed by index. Type something in the first, then delete that item. What happens to the text, and why?

Show answer

The text stays on screen, now belonging to what was the second item. React sees key 0 still exists, assumes it is the same component with new props, and keeps the DOM node — including the input's value, which React never controlled.

With key={item.id}, React sees key 0 has gone, unmounts that component, and the text goes with it. Same data, correct behaviour — the only difference is what you told React the identity was.

3

Move the state instead

In this library, the search dialog holds its query in App's subtree. Find where Search.jsx keeps query, and explain why keeping it there rather than in App matters.

Show answer

query lives inside Search. If it lived in App, every keystroke would re-render the entire application — the masthead, the current page, the whole lesson if one were open.

App holds only searchOpen, a boolean that changes twice per search rather than once per character. That is the general shape: state belongs at the lowest point that can see everything needing it, and no higher.
