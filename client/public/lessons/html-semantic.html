Semantics and accessibility Intermediate

You can build any page out of <div>. The reason not to is that a div tells the browser nothing — and the browser is the thing that has to explain your page to a screen reader, a search engine and a keyboard.

The same page, twice

<!-- Works. Means nothing. -->
<div class="header">
  <div class="nav">...</div>
</div>
<div class="main">
  <div class="post">
    <div class="title">Making bread</div>
  </div>
</div>
<div class="footer">...</div>
<!-- Same layout. Now it means something. -->
<header>
  <nav>...</nav>
</header>
<main>
  <article>
    <h1>Making bread</h1>
  </article>
</main>
<footer>...</footer>

Identical on screen. But in the second version a screen reader user can press one key to jump to the main content, another to list every section, and skip the navigation entirely. In the first they have to listen to everything from the top, every time.

The landmark elements

ElementUse it for
<header>Introductory content — a page or section header
<nav>A block of navigation links
<main>The main content. One per page.
<article>Something self-contained: a post, a comment, a product card
<section>A thematic group, normally with a heading
<aside>Related but tangential — a sidebar, a pull quote
<footer>Closing content for a page or section

The test for <article>: would this still make sense lifted out and shown on its own? A blog post would. A sidebar would not.

In this project

client/src/library/ uses <aside> for the sidebar, <nav> for the lesson list and <main> for the lesson. That is why the "Skip to lesson" link at the top works — it jumps past the whole sidebar. Press Tab as soon as this page loads and you will see it.

Buttons and links are not interchangeable

The single most common accessibility mistake on the web:

<!-- Broken: not focusable, not keyboard-operable,
     not announced as anything -->
<div onclick="save()">Save</div>

<!-- Correct -->
<button type="button" onclick="save()">Save</button>

A real <button> gives you, for free:

  • Tab focus, and a visible focus ring
  • Enter and Space both activate it
  • Screen readers announce "Save, button"
  • A disabled state that actually blocks interaction

Choosing between the two:

  • <a href> goes somewhere. It can be middle-clicked, opened in a new tab, copied.
  • <button> does something on this page.

In client/index.html, the "open the lessons" control is an <a> because it navigates; the theme switch is a <button> because it acts.

Always set type on a button inside a form

A <button> with no type defaults to type="submit". Put an unmarked "Clear" button in a form and clicking it submits the form. Write type="button" unless you mean submit.

ARIA: the escape hatch

ARIA attributes add meaning that HTML cannot express on its own. The first rule of ARIA is not to use it — if a real element does the job, use that instead, because a real element brings behaviour and ARIA only relabels.

The handful that earn their place:

<!-- Names an icon-only control -->
<button aria-label="Delete task">×</button>

<!-- Marks a toggle's current state -->
<button aria-pressed="true">Bold</button>

<!-- Marks the current page in a nav -->
<a href="/about" aria-current="page">About</a>

<!-- Hides decoration from screen readers -->
<svg aria-hidden="true">...</svg>

<!-- Announces content that appears later -->
<p role="alert">Could not save.</p>

<!-- Ties a control to what it controls -->
<button aria-expanded="false" aria-controls="menu">Menu</button>
<div id="menu" hidden>...</div>

All six appear in this project. The delete button on a task is an icon with aria-label; the filter tabs use aria-pressed; the error toast uses role="alert"; the mobile menu button uses aria-expanded.

Keyboard access

Unplug your mouse and try to use your page. Everything interactive must be reachable with Tab and operable with Enter or Space. 

tabindex="0"    <!-- add to the tab order (rarely needed) -->
tabindex="-1"   <!-- focusable by script only, not by Tab -->
tabindex="3"    <!-- never do this -->

Positive tabindex values jump the queue and scramble the tab order for the whole page. If you need a different order, change the order of the HTML.

tabindex="-1" is genuinely useful, though: it lets JavaScript move focus somewhere that is not normally focusable. That is exactly what client/src/hooks/useRouter.js does — when you open a lesson, client/src/library/enhance.js calls .focus() on it, so a keyboard user lands in the new content instead of being stranded in the sidebar.

Never write outline: none

Removing the focus ring makes a page unusable without a mouse — you cannot see where you are. If the default ring is ugly, replace it, do not delete it. Use :focus-visible, which shows the ring for keyboard users but not on mouse clicks. That rule is in client/public/theme.css.

Images, headings, contrast

  • Alt text on every image. Empty alt="" for decoration, which tells the screen reader to skip it.
  • One h1 per page, and never skip a level. Heading structure is how many people navigate.
  • Contrast of at least 4.5:1 for body text. DevTools shows the ratio when you inspect a colour — grey-on-white placeholder text is the usual offender.
  • Never colour alone. A red border on an invalid field is invisible to a colour-blind user; add text or an icon.

Ten minutes of checking

  1. Tab through the page. Can you reach everything? Can you see where you are?
  2. Zoom to 200%. Does anything overlap or get cut off?
  3. Run Lighthouse in DevTools (the Accessibility section). It catches the mechanical problems.
  4. Turn on your OS screen reader — Narrator on Windows (Ctrl+Win+Enter), VoiceOver on Mac (Cmd+F5) — and listen to one screen.

That last one is uncomfortable the first time and it teaches more than any checklist.

Exercises

1

Rewrite the div soup

Replace every div below with a meaningful element:

<div class="page-header">
  <div class="site-title">My blog</div>
  <div class="menu">
    <a href="/">Home</a> <a href="/about">About</a>
  </div>
</div>
<div class="content">
  <div class="post">
    <div class="post-title">First post</div>
    <div class="post-body">Hello there.</div>
  </div>
</div>
<div class="page-footer">© 2026</div>
Show solution 
<header>
  <h1>My blog</h1>
  <nav aria-label="Main">
    <a href="/">Home</a> <a href="/about">About</a>
  </nav>
</header>
<main>
  <article>
    <h2>First post</h2>
    <p>Hello there.</p>
  </article>
</main>
<footer>© 2026</footer>

Note the heading levels: the site title is the h1, so the post title becomes an h2. On a page showing one post you would flip that — the post is the point of the page.

2

Audit the task tracker

Open the app, press Tab repeatedly from the top, and write down what gets focus in order. Can you add a task, tick it and delete it without touching the mouse? Anything you cannot reach is a bug — find out why.

Show answer

Everything is reachable. The delete button is the interesting case: it is invisible until you hover the row, but client/src/styles/app.css also shows it on :focus-visible, so tabbing to it makes it appear. A hover-only control without that partner rule is unreachable by keyboard — one of the most common bugs in otherwise well-built interfaces.

3

Build an accessible toggle

Write a button that shows and hides a paragraph. It must announce its state to a screen reader and say which element it controls — without any CSS.

Show solution 
<button type="button" id="toggle"
        aria-expanded="false" aria-controls="details">
  Show details
</button>

<p id="details" hidden>The hidden details.</p>

<script>
  const button = document.getElementById('toggle');
  const details = document.getElementById('details');

  button.addEventListener('click', () => {
    const isOpen = button.getAttribute('aria-expanded') === 'true';
    button.setAttribute('aria-expanded', String(!isOpen));
    button.textContent = isOpen ? 'Show details' : 'Hide details';
    details.hidden = isOpen;
  });
</script>

Worth knowing: HTML has <details> and <summary>, which do all of this natively with no JavaScript at all — that is what the "Show solution" toggles on this page are. Check for a built-in element before building your own.
