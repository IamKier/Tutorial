Modern CSS Expert

CSS has quietly absorbed most of what people reached for JavaScript and preprocessors to do. This chapter is the handful of features that actually change how you write it.

Container queries

A media query asks how big the window is. That has always been the wrong question for a component, which cares how much room it has. 

.card-area {
  container-type: inline-size;
  container-name: card;
}

.card { display: block; }

@container card (min-width: 30rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

The same card now lays out one way in a narrow sidebar and another in a wide main column — on the same page, at the same window size. Media queries cannot express that at all.

Why this matters more than it sounds

It is the difference between a component that works and a component that works where you put it. Every "this card breaks in the sidebar" bug is a media query being asked the wrong question.

:has() — the parent selector

Selecting an element because of what is inside it was the single most requested missing feature in CSS, for twenty years. 

/* A card that contains an image lays out differently */
.card:has(img) { grid-template-columns: 8rem 1fr; }

/* A field whose input is invalid, styled at the wrapper */
.field:has(input:invalid) { border-color: var(--danger); }

/* A form where nothing is checked */
form:not(:has(:checked)) .submit { opacity: 0.5; }

This project uses it once, and the use is instructive:

.shell:has(.cover) {
  padding-top: 0;
  padding-bottom: 0;
}

The cover needs to fill the viewport exactly, so its container must not add padding. Before :has(), that meant a class toggled from JavaScript — state living in two places to solve a layout problem. Now the parent responds to what it holds, and no JavaScript is involved.

Cascade layers

Specificity fights end with someone writing !important. Layers end them properly, by declaring the order of precedence up front: 

@layer reset, base, components, utilities;

@layer components {
  #sidebar .nav a.link { color: blue; }    /* very specific */
}

@layer utilities {
  .text-red { color: red; }                /* one class — and it wins */
}

Layer order beats specificity entirely. A single class in a later layer overrides an id selector in an earlier one, which is exactly the behaviour utility classes always wanted and never had.

Modern sizing and colour

/* One line instead of two media queries */
font-size: clamp(1rem, 2.5vw, 2rem);

/* Mix in the colours you already have, rather than inventing new hex */
background: color-mix(in srgb, var(--bg) 85%, transparent);

/* Viewport units that account for a phone's collapsing address bar */
min-height: 100dvh;

/* Logical properties: correct in right-to-left languages for free */
margin-inline: auto;
padding-block: var(--space-4);
border-inline-start: 2px solid var(--accent);

color-mix is the quiet one. It means a translucent version of a themed colour without hard-coding an rgba value that then fails to change with the theme — which is how this project's translucent masthead works in both light and dark from one declaration.

Subgrid

The long-standing problem with card grids: each card is its own grid, so the titles in adjacent cards do not line up when one wraps to two lines. 

.cards { display: grid; grid-template-rows: auto 1fr auto; }

.card {
  display: grid;
  grid-row: span 3;
  /* Use the PARENT's rows rather than making my own */
  grid-template-rows: subgrid;
}

Now every card's title, body and footer sit on shared rows, so they align across the whole grid however long the text is. The alternative was fixing heights and clamping lines — which this project does on the book covers, and would not need to with subgrid.

Performance

/* Cheap: the compositor handles these, no layout recalculated */
transform: translateY(-14px);
opacity: 0.5;

/* Expensive: every frame recalculates the position of everything */
top: -14px;
width: 200px;
margin-left: 20px;

Animating transform and opacity costs almost nothing. Animating anything that affects layout forces the browser to work out where every element goes, sixty times a second. That is where jank comes from, and it is why the books on the shelf here lift with translateY rather than margin-top. 

/* Skip rendering work for what is off-screen */
.long-list-item {
  content-visibility: auto;
  contain-intrinsic-size: 0 6rem;   /* a size guess, so the scrollbar behaves */
}

Exercises

1

Media query or container query?

Which fits each, and why?

  1. A page switches from one column to two on a wide screen
  2. A product card shows its image beside the text when it has room
  3. Hiding a decorative sidebar on phones
  4. A comment component used in both a narrow drawer and a wide page
Show answer
  1. Media. A page-level decision about the viewport.
  2. Container. The card cares about its own width; the same card may appear in two places at one window size.
  3. Media. Genuinely about the device.
  4. Container. Precisely the case media queries cannot express.

The test: would the answer change if I moved this component elsewhere on the same page? If yes, it is a container query.

2

Replace the JavaScript

Each of these can be done in CSS or plain HTML. How?

// A
button.onclick = () => panel.classList.toggle('open');

// B
if (card.querySelector('img')) card.classList.add('has-image');

// C
el.style.height = el.offsetWidth * 0.75 + 'px';
Show solution 
<!-- A: the browser owns the state, the keyboard support and the
     screen reader announcement -->
<details><summary>Show</summary>…</details>
/* B */
.card:has(img) { /* … */ }

/* C */
.el { aspect-ratio: 4 / 3; }

C is the sharpest illustration: the JavaScript version reads offsetWidth, which forces a synchronous layout, and then never updates when the element resizes.

3

Find the layout thrash

items.forEach((el) => {
  const h = el.offsetHeight;      // read
  el.style.height = h * 2 + 'px'; // write
});

Why is this slow with a thousand items, and how would you fix it?

Show answer

Every read of offsetHeight after a write forces the browser to recalculate layout immediately, because the answer might have changed. Alternating read and write a thousand times means a thousand forced layouts — layout thrashing. 

// Read everything first, then write everything.
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] * 2 + 'px'; });

Two passes, two layouts. The general rule: batch reads, then batch writes — never interleave them.
