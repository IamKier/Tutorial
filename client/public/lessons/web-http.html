HTTP, requests, responses Basics

Everything between a browser and a server is HTTP. Once you can picture a request and a response, backend work stops being mysterious — it is just a function that takes one and returns the other.

The whole model

   BROWSER                                      SERVER
   your machine                                 could be anywhere
       |                                             |
       |  GET /api/tasks                             |
       | ------------------------------------------> |
       |                                             |  reads data
       |  200 OK                                     |
       |  [{"id":"a1","title":"Buy milk"}]           |
       | <------------------------------------------ |
       |                                             |
   draws the list

Three rules follow from that picture, and they explain most backend design:

  • The browser can only ask. It cannot read your database or your files. It sends a request and waits.
  • The server cannot trust the browser. The browser runs on someone else's machine. Anyone can send any request they like, bypassing your page entirely.
  • Each request stands alone. HTTP is stateless — the server does not remember you between requests. Logins work by sending proof (a cookie or a token) with every single one.

A request

POST /api/tasks HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Content-Length: 24

{"title":"Buy milk"}

Four parts:

  1. Method — POST. What you want to do.
  2. Path — /api/tasks. What you want to do it to.
  3. Headers — metadata. One per line.
  4. Body — the data, after a blank line. GET requests have none.

A response

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 78

{"id":"9f1c","title":"Buy milk","done":false,"createdAt":"2026-08-17T…"}

The same shape, with a status code where the method was.

Methods

MethodMeansBody?Safe to repeat?
GETRead somethingNoYes
POSTCreate somethingYesNo
PUTReplace it entirelyYesYes
PATCHChange part of itYesUsually
DELETERemove itNoYes

That last column has a name — idempotent — and it is why browsers warn you before re-sending a form. Requesting the same GET twice changes nothing. POSTing twice creates two tasks. Deleting twice removes it and then does nothing, which is fine.

Two properties worth keeping straight: safe means it changes nothing at all (GET), idempotent means doing it repeatedly has the same effect as doing it once. A GET that deletes something is a bug — browsers and crawlers pre-fetch links freely.

Status codes

Learn the ranges, then the handful you actually send:

RangeMeaning
2xxWorked
3xxLook somewhere else
4xxYou asked wrongly
5xxThe server broke

The 4xx/5xx split is the one to internalise. 4xx means the caller made a mistake and repeating the request will not help. 5xx means the server made a mistake and a retry might work. Getting it backwards sends people hunting for bugs in the wrong codebase.

200OKIt worked and here is the result

In this project

server.js sends 200 for a list, 201 for a create, 204 for a delete, 400 for an empty title, 404 for an unknown id, 405 for the wrong method and 500 from the catch-all. Precise codes let another developer understand your API without reading its documentation.

Headers

Content-Type: application/json     what the body is
Content-Length: 78                 how many bytes
Accept: application/json           what the client would like back
Authorization: Bearer eyJhbGc…     proof of who you are
Cookie: session=abc123             data the server set earlier
Cache-Control: max-age=3600        how long this may be cached
Location: /api/tasks/9f1c          where the new thing lives (with 201)

Content-Type is the one that bites beginners in both directions. On a response it tells the browser how to treat what you sent — send CSS labelled text/plain and the browser shows it as text instead of applying it, with nothing in the console to explain why. On a request, leave it off and most servers will not parse your JSON body.

URLs

https://example.com:443/api/tasks?status=done&sort=date#section
└─┬─┘   └────┬────┘ └┬┘└───┬────┘ └────────┬──────────┘ └──┬──┘
scheme    host     port   path        query string      fragment
  • Path identifies the resource.
  • Query string modifies the request — filters, sorting, pagination. Starts with ?, pairs joined by &.
  • Fragment is never sent to the server. It is for the browser only, which is exactly why this lesson site can use #/css-layout for routing without ever hitting the network.
// Node gives you a parser — never split URLs by hand
const url = new URL(req.url, `http://${req.headers.host}`);
url.pathname;                      // '/api/tasks'
url.searchParams.get('status');    // 'done'

Watching it happen

Open DevTools (F12) → Network tab → tick the Fetch/XHR filter, then use the app. Click any request:

  • Headers — method, path, status, both sets of headers
  • Payload — what you sent
  • Response — what came back
  • Timing — where the time went

This tab settles almost every "is it the frontend or the backend?" question in about ten seconds. If the request looks right and the response looks wrong, it is the backend. If the request itself is wrong, it is yours.

Two more places to look

The terminal running node server.js logs every request it receives. If a request shows in the Network tab but not the terminal, it never arrived — usually a typo in the URL. And in DevTools you can right-click any request and choose "Copy as cURL" to replay it from a terminal, without the browser involved at all.

Statelessness, and how logins work

The server forgets you the instant it answers. So every authenticated request has to carry its own proof. Two common shapes: 

// Session cookie — the server stores the session, the browser
// sends the id back automatically on every request
Cookie: session=abc123

// Token — the client stores it and attaches it deliberately
Authorization: Bearer eyJhbGciOiJIUzI1NiIs…

Neither is a secret from the network unless the connection is encrypted, which is what the s in https buys you. Over plain http, anyone between you and the server can read every header and every body. Never send credentials over plain HTTP.

Exercises

1

Read the traffic

Open the app with the Network tab recording. Reload, add a task, tick it, delete it. For each of the four requests write down: method, path, status code, and whether there was a request body. Explain why the delete has no response body.

Show answer 
GET    /api/tasks         200   no body sent
POST   /api/tasks         201   {"title":"…"}
PATCH  /api/tasks/<id>    200   {"done":true}
DELETE /api/tasks/<id>    204   no body sent

The delete returns 204 No Content — the deletion succeeded and there is deliberately nothing to send back. A 204 response must not have a body, which is why client/src/api.js checks for that status before calling .json(): parsing an empty body would throw.

2

Pick the right code

What status would you return for each?

  1. Signing up with an email that already exists
  2. Requesting /api/tasks/abc where abc is not a real id
  3. Sending PUT to a path that only supports GET
  4. Your database connection is down
  5. A logged-in user tries to delete someone else's task
  6. A task title of 5,000 characters when the limit is 200
Show answer
  1. 409 Conflict — the request is fine, it clashes with existing state.
  2. 404 Not Found.
  3. 405 Method Not Allowed. Ideally with an Allow: GET header.
  4. 500 (or 503 Service Unavailable if it is temporary). Never leak the internal error text to the client.
  5. 403 Forbidden — authenticated but not permitted. 401 would wrongly imply they need to log in.
  6. 400 Bad Request, or 422 if you distinguish "malformed" from "well-formed but invalid".
3

Bypass the browser

With the server running, send a request from PowerShell — no page, no JavaScript. Then try to create a task with an empty title. What does this prove about client-side validation?

Show solution 
# List
Invoke-RestMethod -Uri http://localhost:3000/api/tasks

# Create
Invoke-RestMethod -Uri http://localhost:3000/api/tasks -Method Post `
  -ContentType 'application/json' `
  -Body '{"title":"From PowerShell"}'

# Empty title — rejected with 400
Invoke-RestMethod -Uri http://localhost:3000/api/tasks -Method Post `
  -ContentType 'application/json' -Body '{"title":"   "}'

The first two work: your API is reachable by anything that speaks HTTP, not just your page. The required attribute in your HTML was never involved. That is why server.js re-validates — client validation is a courtesy to honest users, and the server check is the one that actually protects your data.
