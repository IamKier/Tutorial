Branches and remotes Intermediate

A branch is a movable label pointing at a commit. That is the whole idea, and once it lands, most of Git stops being mysterious.

What a branch actually is

A ─── B ─── C          ← main
             \
              D ─── E   ← feature

main is a label on commit C. feature is a label on E. HEAD is a label saying which branch you are on.

Creating a branch writes a file containing a hash. It copies nothing, which is why it is instant even in a repository with a decade of history — and why the advice is to branch freely rather than treat it as an event. 

git branch                    # list branches
git switch -c feature         # create one and move to it
git switch main               # move back
git branch -d feature         # delete it once merged
switch and restore, not checkout

git checkout does both jobs — moving between branches and discarding file changes — which is how people destroy work while trying to change branch. switch and restore split it in two. checkout still works and older tutorials all use it.

Merging

git switch main
git merge feature

Two things can happen, and they look different in the history:

Fast-forward. If main has not moved since you branched, Git slides the label along. No merge commit, and the history stays a straight line. 

A ─── B ─── C ─── D ─── E     ← main, feature

A real merge. If both moved, Git builds a commit with two parents. 

A ─── B ─── C ───────── F     ← main
             \         /
              D ─── E        ← feature

Conflicts

A conflict happens when both branches changed the same lines. Git does not guess; it stops and marks the file: 

<<<<<<< HEAD
const PORT = 3000;
=======
const PORT = Number(process.env.PORT ?? 8080);
>>>>>>> feature

Above the ======= is what is on the branch you are on; below is what is coming in. To resolve it: edit the file into what you actually want, delete all three marker lines, then git add it and git commit.

The markers are not magic

They are ordinary text that Git wrote into your file. Nothing stops you committing them, and a stray <<<<<<< in a source file is a genuinely common and baffling bug. Search for the markers before committing a resolved merge.

git merge --abort puts everything back if the conflict turns out to be bigger than you thought.

Remotes

A remote is another copy of the repository, usually on a server. Your local repository is complete on its own — the remote is a peer, not an authority. That is what "distributed" means. 

git remote -v                       # which remotes exist
git remote add origin <url>         # "origin" is only a conventional name
git push -u origin main             # send commits; -u remembers the pairing
git pull                            # fetch and merge
git fetch                           # fetch WITHOUT merging

fetch then log is the safer habit: you see what is coming before it lands in your working tree. pull is fetch plus merge in one step, which is convenient right up until it drops a conflict on you mid-thought.

Rebase

git switch feature
git rebase main

Rebase replays your commits on top of another branch, as though you had started from there: 

before:  A ─── B ─── C          ← main
                \
                 D ─── E        ← feature

after:   A ─── B ─── C          ← main
                      \
                       D' ─── E' ← feature

The result is a straight history with no merge commit. The cost: D and E are new commits with new hashes. The originals are gone.

Never rebase what you have pushed

Anyone who pulled the old commits now has history that no longer exists anywhere else. Their next pull produces a tangle that takes someone an afternoon to unpick.

The rule that keeps you out of trouble: rebase your own unpushed work, merge everything else.

A workflow that scales down to one person

git switch -c fix-blank-page     # branch per piece of work
# ... edit, and commit as you go
git switch main
git pull                         # catch up
git merge fix-blank-page
git push
git branch -d fix-blank-page

Working alone this feels like ceremony, and it earns its keep the first time a change turns out to be wrong: the branch is thrown away and main never saw it.

When it goes wrong

git reflog

Every move of HEAD, including the ones that "lost" a commit. Reset too far? Rebased into a mess? The old commit is still there and reflog has its hash: 

git reflog
# e8e21d3 HEAD@{0}: reset: moving to HEAD~3
# 78f75e8 HEAD@{1}: commit: Pin the masthead      ← the one you wanted

git reset --hard 78f75e8

Git almost never deletes a commit. It stops pointing at it, and unreferenced commits survive for weeks before garbage collection. reflog is the first thing to reach for, not the last.

Exercises

1

Cause a conflict on purpose

In a scratch repository, commit a file with one line. Branch, change that line, commit. Switch back to main, change the same line differently, commit. Merge. Resolve it, and check nothing is left behind.

Show solution 
git init && echo "port 3000" > config.txt
git add . && git commit -m "Add config"

git switch -c feature
echo "port 8080" > config.txt
git commit -am "Use 8080"

git switch main
echo "port 5000" > config.txt
git commit -am "Use 5000"

git merge feature              # CONFLICT
# edit config.txt to what you want, removing all three marker lines
grep -c '<<<<<<<' config.txt   # must be 0
git add config.txt
git commit

That grep is worth making a habit. Committed conflict markers are a classic, and they usually surface as a syntax error in a file nobody remembers touching.

2

Lose a commit and get it back

Make three commits. git reset --hard HEAD~2 to throw two away. Confirm with git log that they are gone, then recover them.

Show solution 
git log --oneline          # note the hash of the newest commit
git reset --hard HEAD~2
git log --oneline          # two commits gone

git reflog                 # every move of HEAD, including the reset
git reset --hard <hash>    # the hash from before the reset
git log --oneline          # back

The lesson is not the commands. It is that --hard is far less final than it feels, provided the work was committed. Uncommitted changes are the ones genuinely gone — which is the argument for committing early and often.

3

Merge or rebase?

Which would you use, and why?

  1. Your local branch is three commits behind main. Nothing is pushed.
  2. A colleague has pulled your branch and is working on it.
  3. Bringing a finished feature branch into main on a shared project.
Show answer
  1. Rebase. Your own unpushed work, so rewriting it costs nobody anything, and you get a straight history.
  2. Merge. Rebasing would rewrite commits they already have, and their next pull becomes a mess.
  3. Either, but be consistent. Merge keeps a record that a branch existed and when it landed; rebase keeps the log linear and easy to read. Teams argue about this endlessly — the only wrong answer is doing both at random.
