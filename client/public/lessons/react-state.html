State, effects and hooks Intermediate

Components that only display props are easy. The interesting part is remembering things, reacting to changes, and talking to a server — which in React means hooks.

useState

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

useState returns a pair: the current value, and a function to change it. Calling that function does two things — it stores the new value, and it tells React to render this component again.

That second part is the whole point. This does nothing:

let count = 0;              // ❌ React does not know this changed
count = count + 1;          //    and nothing on screen updates

State updates are not immediate

function handleClick() {
  setCount(count + 1);
  console.log(count);       // still the OLD value
}

count is a value captured when this render ran. Calling setCount schedules the next render; it does not reach back and change the variable you are holding. The new value arrives as a fresh count next time the function runs.

Two updates in a row

setCount(count + 1); setCount(count + 1); adds one, not two — both read the same stale count. When the next value depends on the previous one, pass a function instead: 

setCount((current) => current + 1);
setCount((current) => current + 1);   // now it adds two

Never mutate state

// ❌ nothing re-renders
tasks.push(newTask);
setTasks(tasks);

// ✅ a new array
setTasks([...tasks, newTask]);

// ✅ replacing one item
setTasks(tasks.map((t) => (t.id === id ? updated : t)));

// ✅ removing one
setTasks(tasks.filter((t) => t.id !== id));

React decides whether to re-render by comparing the old value with the new one by identity. Push into the existing array and it is still the same array, so React concludes nothing happened. This is the most common React bug there is, and it fails silently: the data really did change, and the screen simply does not agree.

Controlled inputs

const [title, setTitle] = useState('');

<input value={title} onChange={(e) => setTitle(e.target.value)} />

The input's value comes from state, and every keystroke goes through onChange to update it. The field cannot show anything the state does not contain, which means there is one answer to "what did the user type" rather than two that can disagree.

useEffect

Rendering should be pure: same props and state, same markup, no side effects. Fetching data, setting a timer, adding a listener — all of that goes in an effect, which runs after the render. 

useEffect(() => {
  document.title = `${count} clicks`;
}, [count]);

The second argument is the dependency array, and it decides how often the effect runs:

Written asRuns
useEffect(fn)after every render — rarely what you want
useEffect(fn, [])once, after the first render
useEffect(fn, [a, b])when a or b changes

Cleanup

Return a function and React runs it before the next effect, and on unmount:

useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);

  return () => window.removeEventListener('resize', onResize);
}, []);

Skip the cleanup and every mount adds another listener, all of them still firing. Timers, subscriptions and observers are the same story.

Fetching

useEffect(() => {
  let cancelled = false;

  fetch(`/lessons/${slug}.html`)
    .then((r) => r.text())
    .then((text) => {
      if (!cancelled) setHtml(text);
    });

  return () => {
    cancelled = true;
  };
}, [slug]);

The cancelled flag matters more than it looks. Click quickly between two lessons and both requests are in flight; without the flag, whichever finishes last wins — which may be the one you navigated away from. That is a race condition, and it shows up as content that does not match the page you are on.

Why effects run twice in development

<StrictMode> deliberately mounts each component, unmounts it and mounts it again. It looks like a bug the first time you see two identical requests in the Network tab. It is React checking that your cleanup works — an effect that cannot survive being run twice has a bug that would eventually appear in production anyway.

It does not happen in the production build.

useMemo and useCallback

// Recompute only when tasks changes
const stats = useMemo(() => ({
  total: tasks.length,
  done: tasks.filter((t) => t.done).length,
}), [tasks]);

// Keep the same function identity between renders
const onError = useCallback((message) => show(message), [show]);

Both are caches. useMemo remembers a value; useCallback remembers a function.

Reach for them when a calculation is genuinely expensive, or when a function is passed to a child that would otherwise re-render for no reason. Wrapping everything is a real cost — the comparison is not free, and the code gets harder to read for no measurable gain.

useRef

const inputRef = useRef(null);

<input ref={inputRef} />
<button onClick={() => inputRef.current.focus()}>Focus</button>

Two uses, and they are less different than they look:

  • Reaching a DOM element — to focus it, measure it, or scroll to it.
  • Holding a value that must survive renders without causing one — a timer id, for instance. The screen does not depend on it, so putting it in state would trigger pointless re-renders.

useLayoutEffect

The same as useEffect, except it runs before the browser paints rather than after. 

useLayoutEffect(() => {
  article.innerHTML = html;
  setHeadings(enhance(article));
}, [html]);

That is from client/src/library/LessonPage.jsx. With useEffect the reader saw one frame of raw, unhighlighted markup before it changed under them.

The rule: if an effect measures or rewrites the DOM and the difference would be visible, use useLayoutEffect. Everything else belongs in useEffect, which does not hold up painting.

Custom hooks

A custom hook is just a function whose name begins with use and which calls other hooks. That is the entire rule. 

function useProgress() {
  const [done, setDone] = useState(load);

  useEffect(() => {
    localStorage.setItem(KEY, JSON.stringify([...done]));
  }, [done]);

  const toggle = useCallback((slug) => {
    setDone((current) => {
      const next = new Set(current);   // a NEW Set, not a mutated one
      next.has(slug) ? next.delete(slug) : next.add(slug);
      return next;
    });
  }, []);

  return { done, toggle };
}

They exist so stateful logic can be reused, and so components stay about what is on screen rather than how it got there. In this project useTasks owns the task list and every operation on it, which is why TasksPage.jsx reads as a description of a screen.

The rules of hooks

Call hooks at the top level of a component or another hook — never inside a condition, a loop or a nested function. React matches state to hooks by call order, so a hook that sometimes runs shifts every hook after it onto the wrong state.

Exercises

1

Why does this only add one?

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}

Explain it, then fix it so the count goes up by three.

Show answer

All three calls read the same count — the value captured when this render ran. If it is 0, all three schedule "set it to 1". 

setCount((c) => c + 1);
setCount((c) => c + 1);
setCount((c) => c + 1);

The function form receives the latest pending value rather than the one from render time, so the updates stack.

2

Find the leak

useEffect(() => {
  const id = setInterval(() => setNow(Date.now()), 1000);
}, []);

What goes wrong, and when would you notice?

Show answer

The interval is never cleared, so it keeps firing after the component is gone — calling setNow on something that no longer exists. Navigate back and forth ten times and there are ten intervals running. 

useEffect(() => {
  const id = setInterval(() => setNow(Date.now()), 1000);
  return () => clearInterval(id);
}, []);

You would notice late: it does not crash, it just gradually uses more CPU. This is exactly the class of bug StrictMode's double-mounting is designed to surface early.

3

Write a custom hook

Write useLocalStorage(key, initial) that behaves like useState but survives a reload. It must not throw in private browsing, where localStorage can be unavailable.

Show solution 
function useLocalStorage(key, initial) {
  // A function passed to useState runs once, on the first render only.
  // useState(JSON.parse(...)) would read storage on every render.
  const [value, setValue] = useState(() => {
    try {
      const saved = localStorage.getItem(key);
      return saved !== null ? JSON.parse(saved) : initial;
    } catch {
      return initial;
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // Private browsing, or the quota is full. Losing a saved preference
      // is not worth breaking the page over.
    }
  }, [key, value]);

  return [value, setValue];
}

Compare it with client/src/hooks/useProgress.js, which is the same shape with a Set instead of a plain value.
