Storing and modelling data Intermediate

Data outlives code. You will rewrite the frontend three times and the database will still be the one from year one — so the shape you choose now matters more than almost anything else you decide.

JSON

JSON is how data travels between browser and server, and how this project stores it. It looks like JavaScript and is deliberately smaller: 

{
  "id": "9f1c-4d2e",
  "title": "Buy milk",
  "done": false,
  "tags": ["errand", "urgent"],
  "createdAt": "2026-08-17T08:30:00.000Z"
}

Strings, numbers, booleans, null, arrays, objects. That is all of it.

JSON.stringify(task)           // object -> string
JSON.stringify(task, null, 2)  // pretty, 2-space indent
JSON.parse(text)               // string -> object
What JSON silently loses

There is no date type — a Date becomes a string, and comes back as a string. undefined values and functions are dropped entirely. NaN and Infinity become null. Round-tripping an object through JSON does not always give you back what you put in.

Dates

new Date().toISOString()   // '2026-08-17T08:30:00.000Z'

Store dates as ISO strings, in UTC, always. Three reasons:

  • They sort correctly as plain text — no parsing needed to order them.
  • The Z means UTC, so there is no ambiguity about whose midnight you meant.
  • Every language can parse them.

Convert to local time only when you show it. That is what relativeTime() in client/src/format.js does — the stored value never changes, the display adapts to the reader.

Designing a record

{
  "id": "9f1c-4d2e",
  "title": "Buy milk",
  "done": false,
  "createdAt": "2026-08-17T08:30:00.000Z"
}

Four principles behind that small object:

1. Every record needs an id

Not the title — people rename things. A stable, meaningless id is what everything else refers to. Use a UUID rather than a counter: two requests arriving together can both read "the highest is 4" and both decide to be 5, and sequential ids also tell the world how many records you have.

2. Store facts, not conclusions

❌ { "done": true, "remainingCount": 4, "percentComplete": 60 }
✅ { "done": true }

Anything you can calculate should be calculated. Store it and you now have two sources of truth that must be kept in step — and one day they will not be. the stats memo in client/src/hooks/useTasks.js recomputes the counts and percentage on every draw, and they are therefore never wrong.

3. Choose the type deliberately

❌ "done": "false"     a string that looks like a boolean
❌ "done": 0           a number standing in for one
✅ "done": false

"false" is a non-empty string, so it is truthy. if (task.done) is then true for a task that is not done. That bug is very hard to see and very easy to avoid.

4. Timestamps cost nothing and answer everything

createdAt and updatedAt on every record. You will want to sort by them, debug with them, and answer "when did this change?" eventually. Adding them later means backfilling values you no longer know.

Relationships

Suppose tasks belong to projects. Two ways to express it:

// Nested — the project owns its tasks
{
  "id": "p1",
  "name": "Website",
  "tasks": [
    { "id": "t1", "title": "Design" },
    { "id": "t2", "title": "Build" }
  ]
}

// Referenced — each task points at its project
{ "id": "t1", "title": "Design", "projectId": "p1" }
NestedReferenced
Read one project with its tasksEasyTwo lookups
List every task everywhereHardEasy
Move a task between projectsHardChange one field
A task in two projectsImpossibleStraightforward

Nest when the child genuinely cannot exist without the parent and you always fetch them together — a blog post's tags, an order's line items. Reference for everything else. Referencing is what SQL databases do by default, and it is the safer default here too.

Migrations

The moment you add a field, every record saved before that change lacks it. Add priority to a task and your old tasks have undefined where the new ones have "normal".

Two ways to cope, and you need to pick one deliberately:

// A. Default on read — cheap, works forever
const priority = task.priority ?? 'normal';

// B. Backfill once — run a script that rewrites every record
for (const task of tasks) {
  task.priority ??= 'normal';
}
await writeAll(tasks);

Option A is easier and leaves the mess in place, spread across every piece of code that touches the field. Option B is a one-off effort that leaves the data clean. Real systems do B, in a versioned, repeatable script — which is what the word "migration" means when a framework uses it.

Why a file stops working

src/db/tasks.js reads and rewrites the whole file for every change. That is fine for a few hundred tasks and wrong for anything real:

  • It rewrites everything to change one field. Fifty thousand records, one tick of a checkbox, the whole file written again.
  • There is no way to search except reading it all into memory.
  • Concurrent writes lose data. See below.
  • A crash mid-write can leave a truncated file, and then nothing parses.

The lost update

Open the app in two windows and add a task in each at the same moment:

Request A: reads the file  -> [task1]
Request B: reads the file  -> [task1]           (A has not written yet)
Request A: writes          -> [task1, taskA]
Request B: writes          -> [task1, taskB]    ← taskA is gone

B based its write on data that was already stale. Nothing errored; the task simply vanished.

This is a race condition, and the specific case is called a lost update. It is the reason databases have transactions and locking, and seeing it happen in twenty lines of code you fully understand is worth more than reading ten articles about it.

Moving to a database

SQLite is the right next step, and modern Node has it built in — still no installation: 

import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync('tasks.db');

db.exec(`
  CREATE TABLE IF NOT EXISTS tasks (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    done INTEGER NOT NULL DEFAULT 0,
    createdAt TEXT NOT NULL
  )
`);

// The ? is a placeholder — see the warning below
db.prepare('INSERT INTO tasks (id, title, done, createdAt) VALUES (?, ?, ?, ?)')
  .run(id, title, 0, new Date().toISOString());

const rows = db.prepare('SELECT * FROM tasks ORDER BY createdAt DESC').all();

Notice what you get: it writes only what changed, it can search without loading everything, and it handles concurrent writes properly. All four problems above, solved by the tool built for them.

Never build SQL by joining strings

`SELECT * FROM tasks WHERE title = '${input}'` lets anyone who types ' OR 1=1 -- read your entire table. Use ? placeholders and pass the values separately — the database then treats them as data and never as commands. This is SQL injection, it is the oldest trick in the book, and it still works on new code every week.

This is why db.js is separate

Nothing outside src/db/tasks.js knows that data lives in a JSON file. server.js calls db.createTask(title) and has no idea what happens inside. So switching to SQLite means rewriting that one file — and the routes, the React client and the HTML never notice. That payoff is the entire reason to draw the boundary early.

Exercises

1

Model a library

Design the JSON for a small library: books, members, and loans (a member borrows a book from one date to another). Write one example record of each and say why you nested or referenced.

Show solution 
// books.json
{ "id": "b1", "title": "Dune", "author": "Frank Herbert",
  "isbn": "9780441013593", "copies": 3 }

// members.json
{ "id": "m1", "name": "Kier", "email": "k@example.com",
  "joinedAt": "2026-01-15T00:00:00.000Z" }

// loans.json
{ "id": "l1", "bookId": "b1", "memberId": "m1",
  "borrowedAt": "2026-08-01T00:00:00.000Z",
  "dueAt":      "2026-08-15T00:00:00.000Z",
  "returnedAt": null }

All referenced, because every one of these is looked up on its own: books by title, members by email, loans by "what is overdue?". Nesting loans inside members would make that last question require reading every member.

returnedAt: null rather than a returned: false flag — the timestamp answers both "is it back?" and "when?", and the two can never disagree.

2

Reproduce the lost update

Make it happen deliberately. In src/db/tasks.js, add a two-second delay inside createTask between the read and the write. Then send two creates a moment apart and inspect data/tasks.json.

Show solution 
export async function createTask(title) {
  const tasks = await readAll();

  // Temporary: widen the window where the race can happen
  await new Promise(resolve => setTimeout(resolve, 2000));

  const task = { id: crypto.randomUUID(), title, done: false,
                 createdAt: new Date().toISOString() };
  tasks.push(task);
  await writeAll(tasks);
  return task;
}
# Run both without waiting for the first to finish
Start-Job { Invoke-RestMethod -Uri http://localhost:3000/api/tasks -Method Post `
  -ContentType 'application/json' -Body '{"title":"First"}' }
Invoke-RestMethod -Uri http://localhost:3000/api/tasks -Method Post `
  -ContentType 'application/json' -Body '{"title":"Second"}'

Only one survives. Both requests read the same array, both appended to their own copy, and the second write overwrote the first. Remove the delay afterwards — the race is still there, the window is just narrow enough that you rarely hit it. Narrow windows are what make these bugs so unpleasant.

3

Add a field, handle the old data

Add priority ('low' | 'normal' | 'high') to tasks, end to end: store it, validate it in server.js, add a selector to the composer, colour the card border. Then decide what happens to tasks saved before your change — and implement that decision.

Show answer

The three-layer shape of the change:

// db.js — createTask
priority: ['low', 'normal', 'high'].includes(priority) ? priority : 'normal',

// db.js — updateTask (allow-list, same as the others)
if (['low','normal','high'].includes(changes.priority)) {
  task.priority = changes.priority;
}

// server.js — validate on the way in
const priority = body.priority ?? 'normal';
if (!['low','normal','high'].includes(priority)) {
  return sendJson(res, 400, { error: 'Invalid priority' });
}

For the old records, the cheap fix is defaulting on read (task.priority ?? 'normal'). The clean fix is a one-off backfill that rewrites the file with the field present, after which no other code needs to know the field was ever missing. Real projects do the second, in a script kept in version control — because "temporary" defaults have a way of surviving for years.
