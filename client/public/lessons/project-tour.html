Tour of the project Intermediate

Everything in this course, assembled into one repository — the library you are reading, the task app it dissects, and the server underneath. This lesson walks it in the order that makes it make sense.

The library is entirely static: it fetches lesson files and nothing else. The task app at the demo needs the backend. That difference is why the library can be hosted anywhere and the demo cannot.

The build step

This is the part that surprises people coming from plain HTML. Browsers cannot run JSX — <Cover /> is not JavaScript — so something has to compile it: 

npm run dev      Vite on :5173, the API on :3000, recompiling as you save
npm run serve    compile once into dist/, serve everything from :3000
The files you edit are not the files served

In production the browser never sees client/src/App.jsx. It sees dist/assets/index-hash.js, compiled from it. Edit a component, forget to rebuild, and nothing changes — which is confusing exactly once.

The backend, file by file

No Express. The whole server is about six hundred lines, and each file does one thing.

router.js

"Routing" sounds grand. It is: look at the method and the path, decide which function runs. 

router.get('/api/tasks', taskRoutes.list);
router.patch('/api/tasks/:id', taskRoutes.update);

router.match('PATCH', '/api/tasks/abc-123');
// { handler: update, params: { id: 'abc-123' } }

src/db/

The only place SQL exists. index.js opens the database and runs migrations; tasks.js holds every query.

Statements are prepared once, at module load, and reused. Values always travel as ? placeholders, never interpolated into the string — that is what makes injection impossible.

security.js

Content-Security-Policy, rate limiting, and the check that a state-changing request arrives as JSON. Invisible on localhost; working on every request once the app is reachable by anyone else.

The error convention

throw new HttpError(404, 'Task not found');

Any handler can throw that from any depth, and one place in server.js turns it into a response. Anything thrown that is not an HttpError is a bug nobody anticipated, so it is logged and the caller gets a generic 500 — never a file path or a fragment of SQL.

The frontend

Both applications follow the same rule: state lives in hooks, components handle layout.

HookOwns
useTasksThe task list and every operation on it
useProgressWhich lessons you have read
useRouterWhich page the URL is asking for
useToastThe message at the bottom of the screen

Read client/src/components/TasksPage.jsx and it describes a screen. Read client/src/hooks/useTasks.js and it describes the network. Neither file describes both, and that is the whole point of the split.

The one place React is deliberately not used

Lesson content arrives as a string of HTML from a file, and client/src/library/enhance.js works on it with plain DOM methods — adding syntax colours, Run buttons and heading ids.

A bug worth knowing about

That content was originally rendered with dangerouslySetInnerHTML, which means React owns the element's children and re-applies the HTML on every render. Enhancing it and then calling setState caused React to wipe every change — silently, with no error at all.

The container is now rendered empty and filled in by a layout effect, so React never touches what is inside. The rule: React owns the container, or you own the contents. Pick one.

Adding a task, all the way down

Trace this once and the whole stack clicks into place.

  1. TaskItem.jsx — the form's onSubmit fires. preventDefault() stops the page reloading.
  2. useTasks.js — add() calls api.create(title, dueAt).
  3. api.js — fetch sends POST /api/tasks with a JSON body, then checks response.ok, because fetch will not throw on a 404.
  4. server.js — security headers, the JSON content-type check, the rate limiter, then the router.
  5. router.js — matches POST /api/tasks.
  6. routes/tasks.js — validates: a string, non-empty after trimming, 200 characters or fewer. Otherwise a 400 and it stops here.
  7. db/tasks.js — an INSERT with placeholders, a fresh UUID and an ISO timestamp.
  8. server.js — sendJson(res, 201, task).
  9. useTasks.js — the await resumes and the task the server returned goes into state, not the values that were typed.
  10. React — re-renders the list. The new row animates in.

Ten steps, five files, one round trip. Every feature follows the same path.

What is deliberately missing

  • No accounts. The demo has one shared task list. An earlier version of this project had scrypt hashing and server-side sessions; it was removed when the library became the point. The git history still has it.
  • No pagination, no backups, no logging pipeline. Fine locally, not fine in public.
  • SQLite means one server. Scaling to several means moving to Postgres — a rewrite of src/db/ and nothing else. That containment is the payoff for keeping the SQL in one place.

Exercises

1

Follow a lesson from click to screen

Open the library with DevTools on the Network tab and click a lesson. Which request fetches the content? Then read client/src/library/LessonPage.jsx and list, in order, what happens between that response arriving and the Run buttons appearing.

Show answer

One request, for /lessons/<slug>.html. Then: setHtml stores the text → React renders an empty <article> → the layout effect sets innerHTML → enhance() highlights the code, adds copy and Run buttons, wraps tables and gives every h2 an id → setHeadings hands those ids to the outline.

Note what is not there: no request per code block, and no round trip when you press Run. Everything after the fetch is local.

2

Add a field, end to end

Give tasks a notes field. You will need a migration in src/db/index.js, the column in src/db/tasks.js, validation in src/routes/tasks.js, and somewhere to type it in the React component. Then answer: what happens to tasks saved before your change?

Show answer

They get NULL, because that is what SQLite puts in a new column. Whether that is acceptable is a decision, not an accident — the alternative is a DEFAULT '' in the migration so every row has a value from the start.

The rule that matters: add a new migration, never edit the existing one. An edited migration will not re-run on a database that already applied it, so your machine and everyone else's drift apart silently.

3

Break the isolation, and fail

Find a JavaScript example in this library with a Run button, and try to reach this page from inside it — read document.title, or write to localStorage. Then try an endless loop: while (true) {}. Explain both results.

Show answer

document and localStorage are undefined: the code runs in a Web Worker, which has no DOM and no access to the page that started it.

The endless loop is stopped after two seconds and the page keeps working throughout — because the worker has its own thread and can be terminated. On the main thread the same loop would freeze the tab, and the only cure would be closing it. That is the difference between waiting and working from the Node lesson, demonstrated on something you can actually try.
