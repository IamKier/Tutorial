Getting it online Intermediate

Deployment is where a project stops being yours and starts being something other people can break. Most of the difficulty is not the upload — it is that the server is not your laptop.

The first question: does it need a server?

This decides everything else, and it has a clean test:

StaticNeeds a server
What it isFiles handed out as they areA process that stays running
DataNone, or fetched from elsewhereA database it owns
HostsNetlify, GitHub Pages, CloudflareFly.io, Render, a VPS
CostUsually freeA few dollars a month

This library is static: it fetches chapter files and nothing else, so it can live anywhere. The task app is not — it needs Node and SQLite. One repository, two answers.

A static host cannot run your backend

Netlify and Vercel serve files and short-lived functions. They cannot keep a process alive or give you a disk that survives a deploy. Pushing a Node app there produces a site that builds successfully and does not work — which is a far more confusing failure than one that refuses outright.

The build step

The files you edit are not the files you ship. Vite compiles client/ into dist/, and dist/ is what the host serves. 

npm run build       # client/ -> dist/
npm run serve       # build, then serve everything from one process

A host needs to be told both halves of this, and getting either wrong gives you a blank page with no error: 

# netlify.toml
[build]
  command = "npm run build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "24"

NODE_VERSION matters more than it looks. Hosts default to whatever was current when they last updated, and if that is older than your package.json requires, the install fails with an engine error that reads as though your dependencies are broken.

Configuration comes from the environment

export const PORT = Number(process.env.PORT ?? 3000);
export const DATA_DIR = process.env.DATA_DIR ?? path.join(ROOT, 'data');
export const IS_PRODUCTION = process.env.NODE_ENV === 'production';

Two reasons, and the second is the important one:

  • The same code runs in both places, with only the environment differing.
  • A secret in a source file is in version control, and from there in every clone and every laptop backup, permanently. Deleting it later does not help — it stays in the history.

The disk is not permanent

This is the mistake that costs people real data. Most hosts give each deploy a fresh filesystem. Write your database to the application folder and it is wiped every time you ship a change. 

# fly.toml — a volume that survives deploys
[[mounts]]
  source = "tasks_data"
  destination = "/data"

[env]
  DATA_DIR = "/data"

Which is why DATA_DIR is configurable at all: so the database can be told to live somewhere that persists.

HTTPS, and the headers behind it

You do not usually terminate HTTPS yourself. A reverse proxy does it and forwards plain HTTP to your app: 

tasks.example.com {
    reverse_proxy localhost:3000
}

Caddy gets and renews the certificate on its own. The consequence for your code is that the connection it sees is not the connection the user made — the real scheme and IP arrive in headers: 

x-forwarded-proto: https
x-forwarded-for: 203.0.113.7
Only believe those headers behind a proxy

Anyone can send them. Trusting x-forwarded-for with no proxy in front lets a caller claim any IP address they like, which walks straight past a rate limiter that counts by IP.

Hence TRUST_PROXY being a setting that defaults to off. It is one of the few places where the secure default is also the inconvenient one.

Shutting down without dropping requests

function shutdown(signal) {
  server.close(() => {      // stop accepting; finish what is in flight
    closeDatabase();        // checkpoint the write-ahead log
    process.exit(0);
  });

  // The backstop: if something refuses to finish, leave anyway.
  setTimeout(() => process.exit(1), 10_000).unref();
}

process.on('SIGTERM', () => shutdown('SIGTERM'));

Every deploy sends SIGTERM and then kills the process. Without a handler, whoever was mid-save gets a dropped connection each time you ship.

Why the Dockerfile says node, not npm

CMD ["node", "server.js"] rather than npm start. npm sits between the process manager and your app and does not forward signals properly, so SIGTERM never reaches the handler above and the graceful shutdown you carefully wrote never runs.

A checklist before you expose it

  • Secrets in the environment, never in the repository.
  • A persistent volume mounted where the database lives.
  • HTTPS, with TRUST_PROXY set if something else terminates it.
  • A health endpoint the host can poll — and keep it open, or a monitor getting 401 will restart your app forever.
  • Backups. SQLite is one file, so this is one command — but nothing does it for you.
  • Know what is unprotected. This project's task app has no accounts: anyone who finds the URL can edit everything. That is fine on a private network and wrong in public.

Exercises

1

Static or not?

Which of these can go on a free static host, and why?

  1. A personal blog built from Markdown at build time
  2. A page showing live cryptocurrency prices from a public API
  3. A comment form that stores comments
  4. A photo gallery with images in the repository
Show answer
  1. Static. The Markdown becomes HTML during the build; nothing runs afterwards.
  2. Static. The fetching happens in the reader's browser. Someone else's server does the work.
  3. Not static. Storing anything needs somewhere to store it. Either a backend, or a hosted service that provides one.
  4. Static. Images are files.

The test is not "is it interactive" — it is does the server have to remember anything.

2

Break it the way a deploy would

Run the app, add a few tasks, then delete data/app.db while it is stopped and start it again. What happens, and which deployment mistake does this simulate?

Show answer

The app starts cleanly and every task is gone — migrations run against an empty file and rebuild the schema, so nothing errors.

That is exactly what a deploy without a persistent volume does, every single time you ship. And because there is no error, you find out from a user rather than from a log.

3

Read this project's deployment config

Open netlify.toml. Find the rule that answers /api/* with a 404, and explain why it exists when there is no API on that host anyway.

Show answer

Without it, the catch-all single-page-app redirect matches /api/tasks too and returns index.html with a 200. The frontend then sees a successful response, tries to parse a web page as JSON, and reports "Unexpected token '<'" — a message about the symptom that hides the cause entirely.

A 404 is the honest answer. The client also checks the content type now, so it detects this on any host rather than relying on each one being configured correctly — belt and braces, because this exact bug shipped once already.
