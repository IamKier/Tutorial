SQL and SQLite Intermediate

SQL has outlasted every framework built on top of it, and it will outlast the current ones. An afternoon spent on it pays back for the rest of your career.

Why a database, and why this one

The data lesson ended with a JSON file and four problems: it rewrites everything to change one field, it cannot search without loading the lot, two simultaneous writes lose data, and a crash mid-write leaves a file that will not parse.

This project now uses SQLite, which fixes all four and is built into Node 24 — so it is still not an npm dependency.

SQLite is not a toy

It is the most widely deployed database in the world: every phone, every browser, most desktop software. Plenty of production web services run on it happily. You need a database server like Postgres when you need several application servers talking to one database — not before.

Tables

A table is rows and columns, and every column has a type declared up front. That is the first real difference from a JSON file: the shape is enforced. 

CREATE TABLE tasks (
  id        TEXT PRIMARY KEY,
  title     TEXT NOT NULL,
  done      INTEGER NOT NULL DEFAULT 0,
  dueAt     TEXT,
  createdAt TEXT NOT NULL,
  updatedAt TEXT NOT NULL
);

Reading that line by line:

  • PRIMARY KEY — unique, and the row's identity. One per table.
  • NOT NULL — the database refuses a row without it. A constraint here is worth ten checks in application code, because it cannot be forgotten.
  • DEFAULT 0 — what to use when the column is not supplied.
  • dueAt has no NOT NULL, so it may be NULL — which is how "no due date" is expressed.

SQLite's types are unusual

There are only five: NULL, INTEGER, REAL, TEXT, BLOB. Notably missing:

  • No boolean. Use INTEGER with 0 and 1, and convert at the boundary — see below.
  • No date type. Store ISO strings: they sort correctly as text and are unambiguous about time zone.

The four statements

-- Read
SELECT * FROM tasks;
SELECT id, title FROM tasks WHERE done = 0;
SELECT * FROM tasks ORDER BY createdAt DESC LIMIT 10;

-- Create
INSERT INTO tasks (id, title, done, createdAt, updatedAt)
VALUES ('a1', 'Buy milk', 0, '2026-08-18T09:00:00Z', '2026-08-18T09:00:00Z');

-- Update
UPDATE tasks SET done = 1, updatedAt = '2026-08-18T10:00:00Z' WHERE id = 'a1';

-- Delete
DELETE FROM tasks WHERE id = 'a1';
UPDATE and DELETE without WHERE hit every row

DELETE FROM tasks; empties the table. There is no confirmation and no undo. Write the WHERE clause first, run it as a SELECT to see what it matches, and only then change the verb.

Filtering

WHERE done = 0
WHERE title LIKE '%milk%'          -- % matches any run of characters
WHERE dueAt IS NULL                -- NOT "= NULL", which is never true
WHERE dueAt < '2026-09-01'
WHERE done = 0 AND dueAt IS NOT NULL
WHERE id IN ('a1', 'a2', 'a3')

IS NULL rather than = NULL catches everyone once. NULL means "unknown", and comparing an unknown to anything — including another unknown — yields unknown, never true.

Counting and grouping

SELECT COUNT(*) AS n FROM tasks;
SELECT COUNT(*) AS n FROM tasks WHERE done = 1;

SELECT done, COUNT(*) AS n FROM tasks GROUP BY done;
-- done | n
--    0 | 7
--    1 | 3

That last one is the shape of most reporting: group by something, count within each group. Doing it in SQL rather than by loading every row and counting in JavaScript is the difference between a database and a file.

Placeholders, and why they are not optional

// ❌ NEVER do this
db.prepare(`SELECT * FROM tasks WHERE title = '${input}'`);

// ✅ a placeholder
db.prepare('SELECT * FROM tasks WHERE title = ?').all(input);

With the first version, an input of ' OR 1=1 -- makes the query read WHERE title = '' OR 1=1 --', which matches every row. Worse inputs drop tables or read other ones.

A placeholder is not string-escaping. The value is sent to the database separately from the statement, so it is data and can never be parsed as SQL — no matter what is in it. This is SQL injection, it is the oldest trick in the book, and it still works on new code every week.

Using it from Node

import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync('data/app.db');

// Prepared ONCE, at module load, and reused for every call.
// Preparing parses and plans the query; doing it per request throws
// that work away every time.
const selectAll = db.prepare('SELECT * FROM tasks ORDER BY createdAt DESC');
const insertOne = db.prepare(
  'INSERT INTO tasks (id, title, done, createdAt, updatedAt) VALUES (?, ?, ?, ?, ?)'
);

selectAll.all();              // every row
selectAll.get();              // the first row, or undefined
insertOne.run(id, title, 0, now, now);   // { changes, lastInsertRowid }

Converting at the boundary

function toTask(row) {
  if (!row) return null;
  return {
    id: row.id,
    title: row.title,
    done: row.done === 1,      // INTEGER -> real boolean
    dueAt: row.dueAt,
    createdAt: row.createdAt,
  };
}

Do this once, where the data enters the application, and nothing above ever sees a number pretending to be a boolean. Skip it and JSON.stringify sends 0 to a checkbox that expects false.

Settings that matter

db.exec('PRAGMA journal_mode = WAL');
db.exec('PRAGMA foreign_keys = ON');
db.exec('PRAGMA busy_timeout = 5000');
  • WAL — write-ahead logging. Readers no longer block the writer and the writer no longer blocks readers. The single most valuable SQLite setting for a web app.
  • foreign_keys — off by default, for backwards compatibility. Without it, REFERENCES and ON DELETE CASCADE are decorative.
  • busy_timeout — wait for a lock instead of failing instantly.

Indexes

CREATE INDEX idx_tasks_created ON tasks(createdAt DESC);

Without an index, finding rows means reading every one. With it, the database keeps a sorted structure it can jump into.

Index the columns you filter and sort by — and no more. Every index has to be updated on every write, so indexing everything makes writes slower to speed up queries you never run.

Migrations

The schema changes as the app grows, and those changes have to reach every copy of the database in the same order. SQLite keeps an integer in the file for exactly this: 

const MIGRATIONS = [
  () => db.exec('CREATE TABLE tasks (...)'),
  () => db.exec('ALTER TABLE tasks ADD COLUMN dueAt TEXT'),
];

const { user_version: current } = db.prepare('PRAGMA user_version').get();

for (let v = current; v < MIGRATIONS.length; v++) {
  db.exec('BEGIN');
  try {
    MIGRATIONS[v]();
    db.exec(`PRAGMA user_version = ${v + 1}`);
    db.exec('COMMIT');
  } catch (err) {
    db.exec('ROLLBACK');
    throw err;
  }
}
Never edit a migration that has already run

It will not re-run on a database that already applied it. Your machine and everyone else's then hold different schemas while claiming the same version — and the failure appears somewhere unrelated, weeks later.

Always add a new one. src/db/index.js has a worked example: migration 1 creates a users table that migration 2 drops, and migration 1 was left exactly as it was.

Transactions

BEGIN … COMMIT makes several statements one all-or-nothing unit; ROLLBACK undoes them. A migration that half-applied is the worst state to debug, which is why each one is wrapped.

The same applies in application code: moving a task between projects means two writes, and a crash between them leaves the data inconsistent unless they are in one transaction.

Where this lives in the project

  • src/db/index.js — the connection, the pragmas, the migrations.
  • src/db/tasks.js — every query, prepared once, all values as placeholders.

Nothing outside those two files writes SQL. That is what makes moving to Postgres a rewrite of one directory rather than of the whole application.

Exercises

1

Write the queries

Against the tasks table above, write SQL for each:

  1. Every unfinished task, newest first
  2. How many tasks are overdue (a dueAt in the past, not done)
  3. Every task whose title mentions "report"
  4. Mark every task due before today as done
  5. Tasks with no due date set
Show solution 
SELECT * FROM tasks WHERE done = 0 ORDER BY createdAt DESC;

SELECT COUNT(*) AS n FROM tasks
  WHERE done = 0 AND dueAt IS NOT NULL AND dueAt < ?;

SELECT * FROM tasks WHERE title LIKE '%report%';

UPDATE tasks SET done = 1, updatedAt = ? WHERE dueAt < ? AND done = 0;

SELECT * FROM tasks WHERE dueAt IS NULL;

Note the ? for every date rather than a literal. Even a value you generated yourself goes through a placeholder — it costs nothing and removes the question of whether this particular string was safe.

2

Break it with an apostrophe

In the running app, add a task called Kier's report. It works. Now explain why it would not work if src/db/tasks.js built its SQL with a template literal — and what an attacker would send instead.

Show answer

With a template literal the statement becomes … title = 'Kier's report'. The apostrophe closes the string early, the rest is read as SQL, and it fails to parse — so an ordinary name breaks the app.

That syntax error is the same door an attacker walks through deliberately. '; DROP TABLE tasks; -- closes the string, ends the statement, starts a new one, and comments out whatever followed.

The lesson worth taking: the input that reveals the hole is usually not an attack. It is a customer called O'Brien.

3

Add a column properly

Add a priority column with a default of 'normal'. Write the migration, apply it, and then answer: what do existing rows contain, and what would have happened if you had edited migration 1 instead?

Show solution 
// A NEW entry appended to MIGRATIONS — never an edit to an existing one.
() => {
  db.exec(`
    ALTER TABLE tasks
      ADD COLUMN priority TEXT NOT NULL DEFAULT 'normal'
  `);
},

Existing rows get 'normal', because a DEFAULT on ADD COLUMN is applied to every row already there. Without the default they would get NULL, and NOT NULL would make SQLite refuse the change outright.

Editing migration 1 would have worked perfectly on a fresh database and done nothing at all on yours — the file already reports version 1, so that migration never runs again. You would have two schemas both claiming to be version 1.
