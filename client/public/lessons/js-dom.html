The DOM and events Basics

The DOM is the live tree of objects the browser builds from your HTML. JavaScript changes the page by changing that tree — never by editing the HTML file, which was read once and forgotten.

File versus DOM

"View source" shows the HTML the server sent. "Inspect" shows the DOM as it is right now, including everything JavaScript has added. In the task tracker the task list is empty in the file and full in the inspector. Knowing which one you are looking at prevents a lot of confusion.

Finding elements

document.getElementById('task-list');      // by id, fastest
document.querySelector('.task');           // FIRST match for a CSS selector
document.querySelectorAll('.task');        // ALL matches

// querySelector takes any CSS selector you already know
document.querySelector('#task-form input[type="text"]');
document.querySelectorAll('.task.is-done');

querySelectorAll returns a NodeList, not an array. You can for...of over it, but there is no .map or .filter until you convert: 

const tasks = [...document.querySelectorAll('.task')];
tasks.map(el => el.dataset.id);

Moving around the tree

element.parentElement;
element.children;
element.nextElementSibling;

// The one you will use constantly:
element.closest('.task');   // nearest ancestor matching a selector

closest walks up from an element until it finds a match. It is what makes event delegation work, which is the second half of this lesson.

Changing elements

Content

el.textContent = 'Buy milk';        // as text — safe
el.innerHTML = '<strong>Hi</strong>'; // parsed as HTML — dangerous
This is the one to get right

innerHTML parses whatever you give it as markup. Put a user's text through it and a task titled <img src=x onerror=alert(1)> runs code in every visitor's browser. That is cross-site scripting, and it is one of the most exploited bugs on the web.

The rule is not "never use innerHTML" — it is never use it with anything a user typed. In app.js, task titles use textContent; the fixed SVG icon markup uses innerHTML, because that string is ours.

Attributes and classes

el.getAttribute('href');
el.setAttribute('aria-pressed', 'true');
el.removeAttribute('hidden');

el.hidden = true;        // some attributes are also properties
input.value = '';
checkbox.checked = true;

el.classList.add('is-done');
el.classList.remove('is-done');
el.classList.toggle('is-done');
el.classList.toggle('is-done', task.done);   // force to a boolean
el.classList.contains('is-done');

That third toggle form — with a second argument — is the neatest way to sync a class to a value, and it appears all over app.js.

Custom data

<li data-id="abc-123" data-priority="high">
el.dataset.id;         // 'abc-123'
el.dataset.priority;   // 'high'
el.dataset.id = 'xyz'; // sets data-id

This is the standard place to attach your own data to an element. The task tracker parks each task's id here so a click handler can read it back and know which task was clicked.

Styles

el.style.width = '60%';    // fine for a computed value

Setting styles directly should be rare. Prefer toggling a class and letting CSS decide what it looks like — otherwise your design ends up split across two languages. The legitimate use is a value you can only know at runtime, like the progress bar's width.

Creating and removing

const li = document.createElement('li');
li.className = 'task';
li.textContent = 'Buy milk';

parent.append(li);          // add at the end
parent.prepend(li);         // add at the start
li.remove();                // delete it

parent.replaceChildren();           // remove all children
parent.replaceChildren(a, b, c);    // replace everything in one go
Build once, insert once

Every insertion can make the browser recalculate layout. Appending 100 items one at a time can do that 100 times. Build them into a DocumentFragment — a lightweight off-screen container — or an array, then insert in a single call. Both app.js and learn.js do this. 

const fragment = document.createDocumentFragment();
for (const task of tasks) fragment.append(taskElement(task));
list.replaceChildren(fragment);

Events

button.addEventListener('click', (event) => {
  console.log('clicked', event.target);
});

The ones you will use:

EventFires when
clickClicked, or activated by keyboard on a real button
submitA form is submitted — listen on the form
inputA field's value changes, on every keystroke
changeA field is committed — on blur, or immediately for a checkbox
keydownA key goes down. event.key is 'Enter', 'Escape'…
DOMContentLoadedThe HTML is parsed

The event object

event.target           // the element that was actually clicked
event.currentTarget    // the element the listener is attached to
event.key              // for keyboard events
event.preventDefault() // cancel the browser's default behaviour
event.stopPropagation()// stop it bubbling further up

target versus currentTarget is worth pausing on. If you listen on a <ul> and someone clicks a button inside an <li>, then currentTarget is the <ul> and target is the button.

preventDefault

form.addEventListener('submit', (event) => {
  event.preventDefault();   // stop the full-page reload
  // ...handle it with fetch instead
});

Forms navigate, links navigate, right-clicks open menus. All of that is default behaviour you can cancel. The form case is the one you will write most often — leave it out and the page flashes and resets on every submit.

Bubbling and delegation

An event fires on the element you interacted with, then travels up through every ancestor. Click a button inside an <li> inside a <ul> and all three see the click.

That sounds like trivia. It enables the most useful pattern in DOM work:

// One listener for every task, including ones that do not exist yet
list.addEventListener('click', (event) => {
  const li = event.target.closest('.task');
  if (!li) return;                    // clicked the gap between rows

  const id = li.dataset.id;

  if (event.target.matches('.task__checkbox')) {
    toggleTask(id);
  }

  if (event.target.closest('.task__delete')) {
    deleteTask(id);
  }
});

Why bother, instead of a listener per button?

  • Tasks are created and destroyed constantly. Per-element listeners have to be attached to every new element and cleaned up on every removal.
  • One listener uses less memory than five hundred.
  • It works for elements added after the listener was attached — which is most of them.
matches versus closest

The checkbox uses matches because the click always lands on the checkbox itself. The delete button uses closest because it contains an SVG icon, and clicking the icon makes the <svg> the target, not the button. Missing this produces a button that works everywhere except on its own icon.

The render pattern

Here is the idea that holds a frontend together, and it is worth more than any individual API on this page.

Keep your data in one place. Write one function that draws the screen from that data. When something changes, change the data and redraw. 

let tasks = [];        // the single source of truth

function render() {
  list.replaceChildren(...tasks.map(taskElement));
  countEl.textContent = `${tasks.filter(t => t.done).length} done`;
}

// Every change follows the same two steps
tasks.push(newTask);
render();

The alternative is to reach into the page and tweak the one element that changed. It is faster, and it works until two different things can modify the same element — at which point the page's state and your data quietly disagree and you cannot reason about either.

Redrawing everything is slower and vastly easier to get right. That trade is correct at this size, and React's whole value proposition is doing exactly this, fast enough that you never need the alternative.

Exercises

1

A counter

Build a page with a number, a "+" button and a "−" button. Use a variable as the source of truth and a render() function to display it. Never read the number back out of the DOM.

Show solution 
<p id="display">0</p>
<button id="up">+</button>
<button id="down">−</button>

<script>
  let count = 0;
  const display = document.getElementById('display');

  function render() {
    display.textContent = count;
  }

  document.getElementById('up').addEventListener('click', () => {
    count++;
    render();
  });

  document.getElementById('down').addEventListener('click', () => {
    count--;
    render();
  });

  render();
</script>

The discipline here is not reading display.textContent to find the current count. The DOM is an output, not a database.

2

A list with delegation

A text input, an "Add" button and a <ul>. Adding puts the text in the list with a "remove" button beside it. Use one click listener on the <ul> for all the remove buttons, no matter how many items exist.

Show solution 
<input id="text" /><button id="add">Add</button>
<ul id="list"></ul>

<script>
  let items = [];
  const list = document.getElementById('list');
  const input = document.getElementById('text');

  function render() {
    list.replaceChildren(...items.map((text, index) => {
      const li = document.createElement('li');
      li.dataset.index = index;

      const span = document.createElement('span');
      span.textContent = text;      // textContent, not innerHTML

      const button = document.createElement('button');
      button.className = 'remove';
      button.textContent = 'remove';

      li.append(span, button);
      return li;
    }));
  }

  document.getElementById('add').addEventListener('click', () => {
    if (!input.value.trim()) return;
    items.push(input.value.trim());
    input.value = '';
    render();
  });

  // ONE listener, for every item that ever exists
  list.addEventListener('click', (event) => {
    if (!event.target.matches('.remove')) return;
    const index = Number(event.target.closest('li').dataset.index);
    items = items.filter((_, i) => i !== index);
    render();
  });
</script>
3

Prove the XSS risk

In the app, add a task titled <img src=x onerror="alert('hacked')">. Nothing happens — good. Now edit app.js, change title.textContent to title.innerHTML, reload, and add it again. Change it back afterwards.

Show answer

With innerHTML the browser parses your title as markup, creates a real <img>, fails to load src="x", and runs the onerror handler. An alert box is harmless; the same hole reads cookies, steals session tokens or posts to your API as the logged-in user.

Now notice how thoroughly this is stored: the title went to the server, into tasks.json, and back out again. Every visitor who loads the list runs it. That is a stored XSS, the worst kind — and the entire fix was one word.
