Indexes, plans and transactions Expert

The difference between a query that returns instantly and one that takes thirty seconds is almost never the SQL you wrote. It is whether the database had to read every row to answer it.

What an index actually is

A sorted copy of one or more columns, with a pointer back to the row. The index at the back of a book, and it works for the same reason: you can find an entry without reading the book. 

-- Without an index: read all 500,000 rows, keep the matches
SELECT * FROM tasks WHERE userId = 'abc';

CREATE INDEX idx_tasks_user ON tasks(userId);

-- With one: jump straight into the sorted structure

Indexes are not free, and the cost is the part people forget:

  • Every INSERT, UPDATE and DELETE must update every index on that table.
  • They take disk space, sometimes as much as the data.
  • An index nothing queries is pure cost.

So: index what you filter, join and sort by. Not everything, and not "just in case".

Reading the plan

Stop guessing. Ask the database what it intends to do:

EXPLAIN QUERY PLAN
SELECT * FROM tasks WHERE userId = 'abc' ORDER BY createdAt DESC;
SCAN tasks                          ← reads every row. Bad.
SEARCH tasks USING INDEX idx_...    ← uses an index. Good.
USE TEMP B-TREE FOR ORDER BY        ← sorted the results afterwards. Costly.

Three words tell you nearly everything:

WordMeans
SCANEvery row was read. Fine on a small table, fatal on a large one.
SEARCHAn index was used to jump straight to the rows.
TEMP B-TREEThe results had to be sorted after fetching, because no index provided the order.

Composite indexes, and why order matters

CREATE INDEX idx_tasks_user ON tasks(userId, createdAt DESC);

This one index serves the query above completely: it finds the user's rows and they come out already in the right order, so there is no TEMP B-TREE.

The column order is not arbitrary. A composite index works like a phone book sorted by surname then first name:

QueryUses (userId, createdAt)?
WHERE userId = ?Yes — the leading column
WHERE userId = ? AND createdAt > ?Yes — both, fully
WHERE createdAt > ?No — you cannot look someone up by first name alone

The rule: leftmost prefix. An index on (A, B, C) serves queries on A, on A+B, and on A+B+C — never on B alone.

Things that quietly defeat an index

-- ❌ A function on the column: the index holds titles, not LOWER(titles)
WHERE LOWER(title) = 'buy milk'

-- ✅ Store it the way you search it, or index the expression
WHERE title = 'Buy milk' COLLATE NOCASE
CREATE INDEX idx_title_lower ON tasks(LOWER(title));

-- ❌ A leading wildcard: nothing to jump to
WHERE title LIKE '%milk%'

-- ✅ A trailing one is a prefix, which an index can find
WHERE title LIKE 'Buy%'

The pattern behind all of these: an index can only help if the value you are searching for is what the index actually stores. Wrap the column in anything and the index no longer describes it.

N+1

The most common performance bug in application code, by a distance:

// One query for the books…
const books = db.prepare('SELECT * FROM books').all();

// …and then one more per book. 100 books, 101 queries.
for (const book of books) {
  book.chapters = db.prepare('SELECT * FROM chapters WHERE bookId = ?').all(book.id);
}
// Two queries, whatever the number of books
const books = db.prepare('SELECT * FROM books').all();
const chapters = db.prepare('SELECT * FROM chapters').all();

const byBook = new Map();
for (const c of chapters) {
  if (!byBook.has(c.bookId)) byBook.set(c.bookId, []);
  byBook.get(c.bookId).push(c);
}
for (const b of books) b.chapters = byBook.get(b.id) ?? [];

It hides well: with ten rows in development it is imperceptible, and with ten thousand in production it is a timeout. The tell is a loop with a query inside it.

Transactions

Several statements that must all happen or none of them. The classic is moving something between two places: 

db.exec('BEGIN');
try {
  moveTask(taskId, newProjectId);
  bumpProjectCount(newProjectId);
  db.exec('COMMIT');
} catch (err) {
  db.exec('ROLLBACK');
  throw err;
}

Without it, a crash between the two writes leaves a task in a project whose count does not include it — and nothing will ever notice.

They are also a large speed-up

// Slow: each insert is its own transaction, and each waits for the disk
for (const task of thousandTasks) insert.run(task.id, task.title);

// Fast: one transaction, one flush at the end. Often 100x.
db.exec('BEGIN');
for (const task of thousandTasks) insert.run(task.id, task.title);
db.exec('COMMIT');

The cost of a write is dominated by making it durable — waiting for the disk to confirm. A thousand transactions means a thousand waits; one transaction means one.

Concurrency, and what WAL buys

PRAGMA journal_mode = WAL;

Without it, a writer blocks every reader and vice versa. With it, readers carry on against the last committed state while a write is in progress. For a web application — many reads, occasional writes — this is the difference between usable and not.

What it does not give you is multiple simultaneous writers. SQLite has one writer at a time, which is why busy_timeout exists: rather than failing instantly when another write is in flight, wait a moment and retry.

The lost update, again

Read a row, change it in JavaScript, write it back — and if two requests do that at once, the second overwrites the first. WAL does not prevent this; it is not a locking problem but a logic one. 

-- ❌ read, modify, write
-- ✅ let the database do the arithmetic
UPDATE projects SET taskCount = taskCount + 1 WHERE id = ?;

Exercises

1

Read a real plan

With the app running and a few tasks saved, open the database and run EXPLAIN QUERY PLAN on the listing query, once with the index and once after dropping it. 

EXPLAIN QUERY PLAN
  SELECT * FROM tasks ORDER BY createdAt DESC, rowid DESC;

DROP INDEX idx_tasks_created;
-- run it again
Show answer

With the index: SCAN tasks USING INDEX idx_tasks_created — the rows come out already ordered.

Without it: SCAN tasks followed by USE TEMP B-TREE FOR ORDER BY — every row read, then all of them sorted in memory.

With twelve tasks both are instant, which is exactly why this class of problem ships. Recreate the index afterwards.

2

Which index?

Given these three queries, what is the smallest set of indexes that serves all of them?

SELECT * FROM tasks WHERE userId = ? ORDER BY createdAt DESC;
SELECT * FROM tasks WHERE userId = ? AND done = 0;
SELECT * FROM tasks WHERE dueAt < ? AND done = 0;
Show answer 
CREATE INDEX idx_user_created ON tasks(userId, createdAt DESC);
CREATE INDEX idx_due_done     ON tasks(dueAt, done);

Two, not three. The first serves query 1 completely, and query 2 partly — it finds the user's rows by the leading column, then filters done among them, which is cheap once the set is small.

Query 3 does not start with userId, so it needs its own. Adding a third index for query 2 would slow every write to speed up a filter that was already fast.

3

Measure a transaction

Write a script that inserts 5,000 rows twice — once with each insert on its own, once inside a single transaction. Time both.

Show solution 
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync(':memory:');
db.exec('CREATE TABLE t (id INTEGER PRIMARY KEY, v TEXT)');
const insert = db.prepare('INSERT INTO t (v) VALUES (?)');

let t0 = performance.now();
for (let i = 0; i < 5000; i++) insert.run('row ' + i);
console.log('one at a time:', Math.round(performance.now() - t0), 'ms');

db.exec('DELETE FROM t');

t0 = performance.now();
db.exec('BEGIN');
for (let i = 0; i < 5000; i++) insert.run('row ' + i);
db.exec('COMMIT');
console.log('one transaction:', Math.round(performance.now() - t0), 'ms');

In memory the gap is modest. Point it at a file on disk instead and it widens enormously — because the cost is durability, not the insert. That difference is the whole lesson.
