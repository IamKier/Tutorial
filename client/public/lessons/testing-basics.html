What to test, and why Basics

A test is code that fails when your code is wrong. The hard part is not writing them — it is knowing which ones are worth having, because a suite full of tests that never fail is worse than none at all.

The point

Not "proving the code works". Tests cannot do that. What they do is tell you when you break something you were not looking at — which is most of what goes wrong once a project outgrows one afternoon.

This library has a concrete example of that failing. There was a test asserting a lesson page rendered, and it matched the string prose. That is the container's class, which is always present. Meanwhile the syntax highlighting, the copy buttons and the heading ids were all being created and instantly wiped by React — silently, for weeks. The test was green throughout.

Assert the thing you care about

Not something that happens to sit near it. A test that passes for the wrong reason is worse than no test, because it buys confidence you have not earned.

What is worth testing

Ranked by how much they pay back, in this project's experience:

TestWorth it when
Pure logic Almost always. Cheap to write, fast, and never flaky.
Rules that protect data Always. Allow-lists, ownership checks, limits.
Does it render at all Always. One test, and it catches the whole class of "blank page".
A whole feature end to end For the two or three journeys that matter most.
Every component in isolation Rarely. Slow to write, breaks on every redesign, catches little.

The pattern: test behaviour that would be expensive to get wrong, not every line you wrote. Coverage percentages measure the second and are routinely mistaken for the first.

The shape of a test

import test from 'node:test';
import assert from 'node:assert/strict';

test('deleteTask reports whether anything went', () => {
  // Arrange — set up the world
  const task = db.createTask({ title: 'Delete me' });

  // Act and Assert
  assert.equal(db.deleteTask(task.id), true);

  // Deleting twice is not an error — it is a no-op the second time,
  // which is what makes DELETE safe to retry.
  assert.equal(db.deleteTask(task.id), false);
});

Node has a test runner built in, so this project needs no testing framework at all — npm test and nothing installed.

Note assert/strict rather than plain assert. The non-strict version uses ==, so assert.equal(1, '1') passes. A test that cannot tell a number from a string is not much of a test.

A good test name is a sentence

❌ test('deleteTask', ...)
❌ test('works', ...)
❌ test('test 3', ...)

✅ test('deleteTask reports whether anything went', ...)
✅ test('one user cannot read another user\'s task', ...)
✅ test('an update with no recognised fields changes nothing', ...)

When a test fails, its name is the first thing you see and often the only thing you need. "deleteTask ✗" tells you nothing; "deleting twice is not an error ✗" tells you what was expected and roughly where to look.

Test the edges, not the middle

The happy path usually works — you ran it by hand while writing it. The bugs live at the boundaries:

  • Zero. Empty list, empty string, no results. Division by zero producing NaN is the classic.
  • One. Off-by-one, and the difference between "1 item" and "1 items".
  • Missing. null, undefined, a field the caller forgot.
  • Wrong type. A number where a string was expected.
  • Too much. A 5,000-character title. A million rows.
  • Twice. Deleting twice, submitting twice, the same request arriving again.
Write the test when you find the bug

The most valuable moment to write a test is just after something broke. You know the exact conditions, and you have proof the test can fail — which is the one thing you can never be sure of when writing a test for working code.

Tests that lie

The one that cannot fail

// Passes whatever the function does
test('returns a value', () => {
  assert.ok(getTasks() !== undefined);
});

The one that depends on time

// Passes or fails depending on how fast the machine is
const a = db.createTask({ title: 'First' });
const b = db.createTask({ title: 'Second' });
assert.ok(b.createdAt > a.createdAt);   // same millisecond? flaky.

This project had exactly that. Two tasks created in the same millisecond made the ordering ambiguous, so the test passed or failed depending on the machine. The fix was not to loosen the test — it was to make the ordering deterministic by tie-breaking on rowid. A flaky test is usually pointing at a real ambiguity.

The one that depends on another test

// Passes alone, fails when the suite runs in a different order
test('lists three tasks', () => {
  assert.equal(db.listTasks().length, 3);   // three from... where?
});

Each test must set up what it needs and leave nothing behind. This project's data tests call a reset() first for exactly that reason.

Where the tests live here

test/db.test.js        the data layer: allow-lists, limits, conversions
test/render.test.js    does it actually appear on the screen

Two files, seventeen tests, about four seconds. That is a suite you run without thinking about it — which is the only kind that gets run.

Exercises

1

Find the test that cannot fail

Which of these would still pass if the function were completely broken?

test('a', () => assert.ok(summarise([]) !== null));
test('b', () => assert.equal(summarise([]).percent, 0));
test('c', () => assert.ok(typeof summarise([]) === 'object'));
test('d', () => assert.deepEqual(
  summarise([{done: true}, {done: false}]),
  { total: 2, done: 1, remaining: 1, percent: 50 }
));
Show answer

a and c. Any function returning any object passes both — including one that returns {} and ignores its argument entirely.

b is genuinely useful: it pins the divide-by-zero guard, which is the exact line most likely to be wrong. d is the strongest, checking the whole shape at once.

The tell for a useless assertion: ask "what implementation would fail this?" If the answer is "almost none", delete it.

2

List the edges

For a function splitName(fullName) returning { first, last }, list eight inputs worth testing before you write any code.

Show answer
  • 'Kier Santos' — the happy path
  • 'Kier' — one word, so no last name
  • '' — empty
  • ' Kier Santos ' — extra whitespace
  • 'Kier van der Berg' — three or more parts; where does the surname start?
  • 'Kier-Santos' — a hyphen, which is not a separator
  • null or undefined
  • 12345 — not a string at all

Note that half of these are not "does the code work" but "what should it even do?". That is the real value of listing edges first — it surfaces decisions before you have accidentally made them.

3

Prove a test can fail

In this project, open src/db/tasks.js and delete the AND userId = ?-style guard — the allow-list in updateTask that ignores unknown fields. Run npm test. Then put it back.

Show answer

"updateTask only writes allowed fields" should fail. If it does not, that test is not testing what its name claims.

This is worth doing to any test you have just written. A test you have never seen fail is a test you have never seen work — you have only seen it not complain, and those are different things.
